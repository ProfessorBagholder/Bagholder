# Brief 75: The earlier app gone, every account read one way, and the page saying when the numbers match

For every book and every installed copy. Nothing here depends on any one person's book, machine, count or install. Line numbers are from master at `2255a88` (v2.9.0 plus the decisions commit); the two departures #590 and #592 made while building are folded in and marked "as built". The record is in `briefs/75/`: the three competing designs, the judges, the skeptics' verdicts on each draft, and the migration's SQL (`migration-37.sql`, run clean against an empty copy of the version-36 schema).

## 0. What went wrong

The book is built from Wealthsimple's own rows. The import from the Python app was a stand-in until those rows arrived: in any imported book an import row is superseded as soon as the broker's own row is stored, and stays live only where that row was never stored. The pull had one way of never storing a row: a closed account, once read in full, was never read again (`rust/crates/broker/src/pull.rs:183-194`). The feed can list a closed account's row after that one read, so a book could carry a live import row indefinitely. Instead of removing the premise, two releases built around it: #575 inferred a move's leaving leg from its arrival, and #586 re-read a closed account only "when another row gave a reason". Both were merged without the question whether the premise held. This brief removes the premise, the machinery, the import rows and every line that ever touched the earlier app, for every book alike.

## 1. The design

1. **One book migration** deletes every import row in every state and everything derived from it, drops the two columns that existed only for the earlier app, clears the book's record of which accounts were read, and, in a code step of the same migration, splits any book account the import built from several broker accounts back to one account per broker id. It runs once per book, inside one transaction, with every reference checked before it commits (`rust/crates/sqlite/src/migrate.rs:191-194`, `:201-213`, `:231`), after the book has been copied to `snapshots/` as every migration already does (`migrate.rs:1-20`). It reports what it found and did in the start log: rows by state, trades orphaned, accounts split.
2. **The next sync starts at once and reads every account whole,** closed ones included. Whatever rows the broker lists for each account come in as its own records. From then on the book holds the broker's records, the person's own records, and nothing else.
3. **Every account the broker lists is read the same way on every sync** (the owner's decision of 2026-10-21): from its last full read, whole where it has none. No closed-account rule, no reasons, no inference.
4. **A closed account is held to what closing means:** it holds nothing. That is stored as the broker's statement for it, by the sync and by the five-minute balances pass alike, so the check that compares every open account's cash and holdings with the broker covers closed accounts the same way. No new request.
5. **Withdrawn on 2026-10-22.** This item proposed a visible line in the header ("Matches Wealthsimple as of <day>"). It was built as #592 and reverted at the owner's word: "that's not in alignment with any UI/UX practice, I did not request it, and it will look stupid and ugly." Nothing visible is built from a brief without the owner asking for it. What assures the figures is what exists: every difference with the broker is said in the header with both figures once confirmed (§5).
6. **Every reader and writer of the earlier app's file is deleted in the same release,** with #575's and #586's pull machinery and the pull's own import-replacing code. About 25,700 lines go; about 500 hand-written lines come in, of which about 250 leave again with the migration.
7. **The release after** folds the migrations and their schema snapshots into one base schema, and the migration's code leaves with them. A book not yet opened by 2.10.0 is refused with one sentence naming the step. Every copy, however old, is carried through that step by the updater it already runs (§6). This is the pattern Django, Rails and GitLab document.

**The invariant the whole design is held to:** after the migration and its first sync, a book that was imported is indistinguishable, in structure and in figures, from a book synced fresh from the same broker accounts. Test 1 holds it over generated books of every kind (§7).

Nothing runs at every start. Nothing waits on a condition. Nothing of the earlier app remains in code that runs, in any book, or in the data folder's use, with three things named so they are known: the first event of orders and brackets a book carried from the earlier app stays readable in that book's order log (§3); the old model crate, which the live wire types still reference, is its own plan (§11); and the folder and archive names carrying `rust` are left alone because the updater finds releases by them (§11).

## 2. What happens to a book, by kind

A superseded or removed import row has no transactions, because the book deletes them before it marks a record superseded or removed (`rust/crates/book/src/records.rs:502-507`, called at `links.rs:93` and `records.rs:486`), so it counts in no figure in any book. No writer in the current code can anchor a trade on such a row: supersede moves or orphans every anchored trade first (`links.rs:58-74`), removal orphans them first (`records.rs:478-480`), and a trade can only be opened on a transaction that exists (`trades.rs:59-61`). A live import row may anchor a trade; the migration orphans it with its note kept, as Clear data does (`rust/crates/book/src/clear.rs:165-169`), and counts it in the log.

| The book | The migration | Until the first sync ends | The first sync |
|---|---|---|---|
| Fresh, never imported | finds nothing to delete; drops the columns; clears the read marks | figures unchanged; `Not yet checked against Wealthsimple` | every account read whole, as a first sync always is; then `Checking`, then `Matches` at the next balances pass |
| Imported, no live row | every import row and its derived rows go; no figure moves | figures unchanged; `Not yet checked` | as above |
| Imported, live rows (any number, any account) | the same, plus each live row's transactions; a trade anchored on one is orphaned with its note kept and counted | any figure that rested on a live row is off by that row: a transfer leg counted once too many, a holding, a balance; `Not yet checked`, nothing positive said | each account read whole; the broker's own rows for what the live rows held come in, and the figures are right; a row the broker does not list leaves a difference the header names in red once the balances pass confirms it |
| Imported, with accounts the import pooled | each pooled account is split to one account per broker id (§4), its history rows cleared so every part is read whole | the split accounts show no history until the sync | each account's activity, history and statements read whole; trades and notes keep their anchors |
| A trade an earlier build left anchored on an import row | orphaned with its note kept, counted in the log | the note sits on an orphaned trade, listed as such | the broker's row opens the trade afresh; the note stays on the orphaned one, as Clear data leaves it |
| Cannot reach the broker (no session on disk) | the same as its kind above | the same, until a sign-in; the header reads `Not connected` | the sign-in's first pull reads everything whole |
| Docker | the same; the image migrates the volume's book on start | the same | the same |

Every copy: the old file `bagholder.db` is never opened again; it stays where it is for the person to delete. `snapshots/` keeps the two newest copies as it does for every migration (`migrate.rs:55`). If the migration fails, the book stays at version 36 and the page says so (`migrate.rs:16-17`).

**What the window costs, for any book:** between the migration's commit and the end of the first sync, one sync's worth of time; the header says nothing positive meanwhile. **What the first sync costs:** one feed page per hundred rows per account (`rust/crates/wealthsimple/src/client.rs:241`), paced at 150 ms (`client.rs:18`), and every stored broker row read again under the new rule set; measured by the capacity job at the reference size it documents, a stated number of accounts, instruments, trades and months chosen as the size every book is held to, with four times it as the growth rule (`rust/crates/server/src/capacity.rs:9-10`), against the 5 s first-figure budget (`capacity.rs:38`), and stated in the PR. A book beyond the reference size is covered by the growth rule, not by the budget.

## 4. The pull: one rule, the split, and what is reverted

**The rule.** For every account the broker states, open or closed: read its activity from its last complete read, lowered to the first day of any row of it stored before it was final (`pull.rs:215-222`, the only lowering left), whole where it has no complete read. The `closed`/`to_read` split, `closed_read`, `since` and `closed_due` go (`pull.rs:183-209`, `:220-221`, `:565-598`). Today the balances and statements are read only for open accounts (`pull.rs:365`, `stated.iter().filter(|a| a.open)`; `:377-384`); after this they are read for every account the broker lists, closed ones included. The book's account status follows the broker's on every pull: today it is written only when the account is added (`pull.rs:125-126`, `rust/crates/book/src/identity.rs:86-88`, and no `UPDATE accounts` sets it anywhere), while the five-minute balances pass keys off it (`pull.rs:909-911`), so an account the broker reopened would never be re-read. One update where it differs.

**A closed account's statement.** The broker's `closed` is stored as a cash statement of nothing (`Book::store_cash`, `rust/crates/book/src/statements.rs:286-296`, with an empty map) and a units statement of nothing (`store_units`, `:513-525`, once as of the pull's day when first stated closed), by the sync and by the five-minute balances pass (`pull.rs:905-913`, which today skips every account the book holds as not open). The second matters: a cash difference is said only once a balance stated after the activity read confirms it (`rust/crates/engine/src/equity.rs:159-166`, `rust/crates/server/src/status.rs:213`), and the sync stamps its statement and its read with the same instant (`pull.rs:226`, `:352`, `:1055`), so a statement stored only by the sync would leave a closed account's difference pending forever, which is why the page is silent about closed accounts today. The units check runs once a units statement exists, an empty one included (`equity.rs:179`; `rust/crates/server/src/engine_inputs.rs:243`). This follows what the statements module already assumes of a closed account (`rust/crates/broker/src/statements.rs:921-926`, the code at `:931`). No request. The design is right whichever balance the broker would answer for a closed id: a difference is said. The verification path is a recorded reply of a closed account in the replay fixtures (`rust/crates/wealthsimple/src/replay.rs:1-6`, the files `ws-anonymise` writes), contributable from any capture, with the adapter's handling of both possible answers stated as a rule; no recorded reply holds one today.

**Accounts the import pooled: split, in every book.** The import is the only thing that ever put several broker ids on one book account: `add_account` refuses an id another account holds (`rust/crates/book/src/identity.rs:61-75`), the pull and manual entries add one ref (`pull.rs:119-128`; `rust/crates/server/src/entries.rs:204`), and only the import passes several (`rust/crates/book/src/import/mod.rs:218-256`, `add_account_ref` at `:238`). The broker does not merge accounts: its `linkedAccount` is recorded as a link row and nothing more (`rust/crates/wealthsimple/src/read.rs:71-72`; `pull.rs:132-137`). The pull carries the pooled case as "one book account can be several of the broker's (the import joined them)" (`pull.rs:361-367`, `:374-384`), summing their balances, net values and history. A migrated book has to look like a fresh one, so the migration splits every pooled account:
- **A code step of migration 37, not a repair at open.** A leg's account is the mapping's output (`records.rs:247`, `:352`; `mapping.rs:256`, `:1069`), and the mappings are assembled in the server (`rust/crates/server/src/figures.rs:886-888`), which the book crate cannot see. So the migration runner gains one optional code step per migration (`Migration` is SQL text today, `migrate.rs:28-32`; the step is a function run after the SQL and before the reference check, inside the same transaction, `:218-236`), and `Book::open_in` (`rust/crates/book/src/lib.rs:119`) takes the steps from its caller: the server passes the split, bound to its mappings, at `figures.rs:400`. The step is a book-crate function taking the connection, the mappings (`rust/crates/book/src/mapping.rs:30`) and the instant; it mints ids as the book does (`lib.rs:182`). It runs exactly when migration 37 runs, is recorded with it, and is never checked again: no settings flag, nothing at later starts. The repository's other shape for this, a repair at open under a `repair.<name>` key (`identity.rs:753`, `trades.rs:288-296`), is a standing condition and is not used. This is Django's `RunPython` and Rails' data migrations (§10).
- **What the step does**, for each book account holding more than one `account_refs` row: keep the first id on the existing account; for each other id, add an account with the pooled row's `connection_id`, `kind`, `registration`, `managed`, `joint`, `unrecognised_type`, `status` and `nickname` copied (the import pooled only where the stated types agreed, `import/mod.rs:206-218`) and move that `account_refs` row to it; then, for every live record with a transaction or hold in the pooled account, map its latest revision with its source's mapping, resolve each leg's and hold's account ref as derive does (`records.rs:352-355`), and update `transactions.account_id` and `record_holds.account_id` in place. In place, not by re-derivation: a trade's opening key includes the account (`records.rs:93-98`), so a re-derive that moved a leg to another account would orphan its trade (`records.rs:309-331`), while an in-place update keeps every anchor; and the step runs inside the migration, before the re-derivation at open (rule set 14, below), so derive then finds the same account before and after. A record whose legs cannot be resolved stays on the kept account and is said as a problem, as derive says it. The change-log triggers fire on the moved rows (`rust/crates/book/schema/v36.sql:650-668`, `:941-950`); the engine builds whole at open and reads the log only from there (`rust/crates/book/src/changes.rs:45-50`), so they cost nothing. Orders need nothing: they store the broker's own account id (`v36.sql:383`, `orders.rs:26`, `:76`). Monthly statements are keyed by the broker's key (`v36.sql:336-343`).
- **The pooled account's history rows** (`account_days`, `account_values`, `statements` with `statement_cash`, `statement_units`, `statement_holds`, `buying_power`, `margin_backing`, `account_links`, `activity_reads`) are deleted for it, and the `statements.said` setting with them as Clear data does (`clear.rs:202-204`), so the first sync reads every part whole: an account with no stored day is read whole (`pull.rs:489-493`), with no activity read likewise, `margin_backing` is rebuilt by every accounts read (`statements.rs:183-195`), and `account_links` are only ever added (`:176-178`), which is why the migration deletes the pooled account's. Every table that references `accounts(id)` is one of these (`v36.sql:46`, `:55-56`, `:63`, `:67`, `:97`, `:170`, `:331-332`, `:442`, `:550`, `:617`).
- Held by test 1 over generated books with pools of two and three ids (the import fixture makes them, `rust/crates/book/tests/import.rs:137-141`, `:450-466`): after the migration and a sync against a generated broker, every account's units and cash equal the broker's per id, every trade keeps its anchor, every note its trade, and the book equals a book synced fresh.
- No pull can meet a pooled book: the step runs inside `Book::open`, before the figures exist, and the broker loop waits for the figures (`broker_reads.rs:125`).

**The linked-set rule, added 2026-10-23.** After 2.10.0 a book showed one TFSA as two accounts disagreeing with the broker: the broker's accounts list names each id as the other's `linkedAccount` (an account given a new id, the old one closed), which the pull had recorded in `account_links` and nothing read; the import's pooling had been that fact by accident, and this brief's §11 wrongly called the links a presentation question. The rule, from the broker's own statement, for every book: **one book account per set of broker ids the broker links as one** (a connected component of `account_links` within a connection). The split stands for ids the broker does not link. Migration 39, a code step beside `pooled::split` and its inverse for linked sets only, merges each linked set the split separated back onto the oldest account (its id kept; status open if any id is open; type and nickname the open id's, else the newest's; the set's history rows deleted so the next sync reads it whole); it fails whole on anything it cannot place. The pull holds the rule on every pull: an id the broker links to an account the book has goes to it, two book accounts the broker links are merged by the same step, and `account_links` is rebuilt from each accounts read. A linked set's statements and balances are read per id and summed, the path that existed for the import's pooling. Released as 2.10.2 (PATCH).

**The rule's stated limit.** The broker's feed is asked by `startDate` (`client.rs:235-241`), and nothing in the repository says whether it applies to a row's `occurredAt` or to when the row was posted. Under the code's own reading, a row the broker adds later under an older date, in any account, is not asked for by an incremental read. Every vendor that documents this says a date window is not enough: Plaid, "a removed transaction will no longer appear in /transactions/get" and "a posted transaction cannot necessarily be considered immutable"; Teller, "When a pending transaction posts, its date often changes to the posting date"; Akahu, "banks often mutate a transaction in the days (or weeks) following its posting" (§10). Wealthsimple offers no cursor. So the catch is where bank reconciliation puts it: the balances. A cash difference is confirmed by the next balance and said; a units difference is said as of the day read; the monthly statements are read for any account whose cash differs, and the movements the feed left out are booked from them (`rust/crates/broker/src/statements.rs:1-20`). The way to read everything again is the one the app has: `Clear data` → `Wealthsimple records`, journal kept (`SPEC.md` pages-24). No re-read driven by a reason is added (the owner's decision of 2026-10-21).

## 5. How anyone is assured the numbers are right, on the page

What exists, and stays the whole of it: after every change to the figures, the engine compares each account's cash per currency with the cash the broker stated, and its units with the broker's units as of the day of the last full read (`rust/crates/engine/src/equity.rs:130-214`); a confirmed difference is said in the header with the account and both figures (`rust/crates/server/src/status.rs:201-237`), as is a month whose statement does not reconcile, and every sale beyond what was held. With #590 that check covers closed accounts too (§4), which is what this brief changes about assurance.

The positive, dated line this section first proposed was built as #592 and reverted at the owner's word (§1, item 5). Whether a reconciled state should ever be shown, and how, is the owner's decision; nothing of it is proposed here.

## 6. Releases, versions and the upgrade path for any copy

- **2.10.0 (MINOR):** §§1-5. Something new a user can see (the header line), nothing an existing install relies on breaks: every book is migrated with a snapshot, and no Rust install ever relied on the Python app's file. `CLAUDE.md`'s rule.
- **3.0.0 (MAJOR):** the base schema. A book last opened by a version before 2.10.0 is refused until 2.10.0 has opened it, which breaks an install that skips 2.10.0.

The pattern, from the projects' own documentation: Django, "squash, keeping the old files, commit and release, wait until all systems are upgraded with the new release … and then remove the old files, commit and do a second release"; Rails, the schema file "is the authoritative source for rebuilding that database. This makes it possible to delete or prune old migration files"; GitLab squashes migrations at each required upgrade stop, "versions of GitLab that you must upgrade to before upgrading to later versions"; Home Assistant keeps migration code six releases and says "update in increments of no more than 6 releases at a time".

**How any copy gets through the stop.** Today every copy asks GitHub for the latest release only (`rust/crates/server/src/update.rs:36-38`), reads no release notes (`:121-129`), and offers any newer tag (`:248-250`; the fetch and its ETag at `:214-230`), every two minutes (`:29`). A copy that installed 3.0.0 straight from 2.9.x would start, have its book refused, stay up (a stored-data failure never stops the server, `main.rs:258-262`), outlive the 20 s window, and so lose `previous/` and `snapshots/` (`update.rs:944-955`) with no way back in the app. Two mechanisms, one for the updaters that exist and one for the updaters from 2.10.0 on, carry every copy through:
- **GitHub's "latest" mark stays on the oldest required stop** (2.11.0, as released). The only request an existing updater makes is for the release GitHub marks latest, and GitHub lets a later release be published without taking that mark (the releases API's `make_latest`, values `true`, `false` and `legacy`; `gh release create --latest=false`). So 3.0.0, and every release after it while 2.10.0 is the oldest stop within the support window, is published with the mark left on 2.10.0: a copy on any earlier version is offered 2.10.0, installs it, and from then on runs the updater below. `release.yml:131-144`, which today marks every release latest once its archives exist, marks only a stop. The support window is a stated rule in the README: a copy more than twelve months behind the newest stop installs by hand, as Home Assistant states its own window; GitHub's own releases page then shows "Latest" on the stop, and the README says so.
- **Updaters from 2.10.0 on walk the stops themselves.** A stop is marked on the release as an asset named `bagholder-vX.Y.Z-stop`, uploaded by the release step in `CLAUDE.md`'s release command, not by the build matrix (`release.yml:116-120` uploads archives per platform; `release_assets`, `update.rs:297-312`, matches only the archive and its checksum, so the marker is never taken for one). The updater lists releases (`releases?per_page=100`, one request, the ETag as today), skips drafts and prereleases, and offers the oldest stop newer than the running version before the latest (about 40-70 lines with tests). A copy below a stop is offered the stop, installs it, and at its next check is offered the next. The container copy, which runs the same check (`:248`), is told the stop's version in its header instead of the latest. The first release carrying this updater is marked a stop (2.11.0, as released; see §9 step 5).
- **A refused-as-too-old book during an update's window exits the new server with the failure,** taken only on that refusal and only while `update-pending` exists (`update.rs:920`); every other stored-data failure keeps the server up (#516, `main.rs:258-262`). The supervisor still running is the version already installed: it puts that version back (`update.rs:962-985`) and its header says, in its own words, `Update failed: vX did not start.` The step to take reaches such a copy through the README and the release notes, never through that header; with the latest mark on the stop, no existing updater takes this path at all, and a copy on 2.10.0 or later is never offered a release past a stop it has not reached. The migration runner's refusal of an older book is one new arm in `identify` beside `Newer` (`migrate.rs:149-168`); the book is looked at read-only and left exactly as found (`:123-127`), so no snapshot is at stake.
- **Docker:** `docker compose pull` on `:latest` jumps to the newest image; the image carries no updater (`rust/Dockerfile:48-56`). A container coming from before 2.10.0 sees its book refused with the sentence, the volume untouched, and the way through is written in the compose file's comment and the README: pin `image:` to `:2.10.0`, start once, return to `:latest`. The header of a container on 2.10.0 or later names the stop (above).
- README's "Keeping up to date" (`README.md:149-165`, which also still says "once an hour" where the code checks every two minutes, `update.rs:29`; the doc comment at `update.rs:990` says the same) gains the rule, the window and the sentence a refused book shows.

**When 3.0.0 ships** is a stated rule, not anyone's installs: not before the stop release has been the latest release for 90 days, and never without the latest mark and the stop asset in place.

**What 3.0.0 changes in the migration runner.** Today a new book is built by running every change in order (`migrate.rs:134-142`, `:216`). After 3.0.0 it is built from one file holding the finished layout, and the change files are deleted. A book not yet brought to the base version is refused with the sentence. One small fix is needed in how the layout file is written out, because today it lists an index before the table it belongs to (`migrate.rs:323`, `ORDER BY type, name`), and the runner's own application id and `schema_migrations` row, written only for migration 1 today (`:218-229`), are written for the base. About 70 lines with tests. The cache store passes no base and is unchanged. This is a change to how stored data is opened, so it goes through the gate as its own plan.

**Docs amended in PR 2, the same PR as the migration:** `docs/decisions.md`'s 2026-10-21 entry ends "Held by: the scan for the earlier app's identifiers (plan #573), once built"; the owner's refusal of that scan (2026-10-21) is recorded there and the holder becomes test 9 and review. `docs/architecture.md` §6, "Schema changes never lose data", gains the sentence: a migration may delete rows that count in no figure, by the owner's decision of 2026-10-21, after a snapshot. `docs/plans/remove-the-earlier-app.md` is marked superseded by this brief. `SPEC.md` market-data-11 says "every account, open or closed"; `docs/plans/stage-3b-wealthsimple.md:63` loses "nothing for a closed account with no new activity". Every size, rate, depth and share the capacity job is held to is restated as a documented reference figure chosen for every book, its derivation noted only as a dated sample; no name, constant or comment in `capacity.rs` (`:1-2`, `:66-81`, `:137`, `:153`, `:437`, `:459-463`, `:546`, `:582-589`) or `replay.rs` (`:4-5`) refers to any person's book.

## 8. Risks, said plainly

- **Stating a closed account as holding nothing** rests on what closing means and on `statements.rs:921-931`; no recorded reply shows what the broker answers for a closed id. If it ever states otherwise, the check says a difference, which is the right outcome.
- **The window between the migration and the end of the first sync**, for any book with a live import row: the figures that rested on it are off for one sync, with the header saying `Not yet checked`. With no session on disk it stays so until a sign-in.
- **The first read after the migration has nothing older to compare with.** When a read lists fewer rows than the book holds, the app refuses to delete more than three final rows at once and says so (`pull.rs:547`, `:641-655`); after the migration that three-row limit is the only guard, as on any first read or after Clear data. Any removal is listed in the pull's log.
- **A late row in an open account** dated before its last full read: §4's limit. Caught by the balances, said once confirmed, read again on `Clear data` → `Wealthsimple records`.
- **The split** moves nothing but the refs, the per-leg account of transactions and holds, and the history rows it clears; a record whose legs cannot be resolved stays on the kept account and is said as a problem, as derive says it. The test's fresh-book comparison is what proves the step.
- **`carry_told_by_listing`** (`carry.rs:382-423`, a one-time repair of notification marks from an earlier Rust build) is retired, not moved. The property that makes this safe is in the code, not in which copies ran it: a scope with no mark sets one without telling (`main.rs:180-182`), so a book that never ran the repair tells nothing twice; test 12 holds it. Its old-form `told` rows stay as inert rows.
- **The latest mark on the stop** relies on GitHub honouring `make_latest: false`, which its API documents; the release step checks it after publishing. A copy more than the support window behind installs by hand, as the README states.
- **Cost:** one feed request per closed account per sync; once, every account read whole and every stored row read again at the first start, measured at the reference size and four times it against the 5 s first-figure budget, and stated in the PR.
