# Brief 75: The earlier app gone, every account read one way, and the page saying when the numbers match

Written for the owner first, then for the CTO. Every line number is from master at `2255a88` (v2.9.0 plus the decisions commit). Three independent designs were drawn from verified readings of the code and of outside practice, scored by two judges, and the load-bearing claims of this brief were then checked against the code by eleven skeptics; their corrections are in. The record is in `briefs/75/`, and the migration's SQL is `briefs/75/migration-37.sql`, run clean against an empty copy of the version-36 schema.

## 0. What went wrong, in one paragraph

The book is built from Wealthsimple's own rows. The import from the Python app was only ever a stand-in until those rows arrived, and all but one of its rows have been replaced by them. The one still live is the leaving side of the cash move out of the closed managed RESP on 2025-06-16. Wealthsimple's feed lists that row today. The book never stored it because of one wrong premise in the pull: a closed account, once read in full, is never read again (`rust/crates/broker/src/pull.rs:183-194`). Instead of removing the premise, two releases built around it: #575 inferred the leaving leg from the arrival, and #586 re-read a closed account only "when another row gave a reason". I cleared both; I should have asked whether the premise held. Each added machinery to keep an import row counted instead of reading the broker. This brief removes the premise, the machinery, the import rows, and all the code that ever touched the earlier app.

## 1. The design, in plain words

1. **One book migration** (number 37) deletes every import row and everything derived from it, drops the two columns that existed only for the earlier app, and clears the book's record of which accounts were read. It runs once per book, inside one transaction, with every reference checked before it commits (`rust/crates/sqlite/src/migrate.rs:191-194`, `:201-213`, `:231`), after the book has been copied to `snapshots/` as every migration already does (`migrate.rs:1-20`).
2. **The next sync starts at once and reads every account whole,** closed ones included. The leaving row of the 2025-06-16 move comes in as Wealthsimple's own record, and the book is then built from Wealthsimple's records and nothing else.
3. **From then on, every account the broker lists is read the same way on every sync** (your decision of 2026-10-21): from its last full read, whole where it has none. No closed-account rule, no reasons, no inference.
4. **A closed account is held to what closing means:** it holds nothing. That is stored as Wealthsimple's statement for it, by the sync and by the five-minute balances pass alike, so the check that already compares every open account's cash and holdings with Wealthsimple covers closed accounts the same way. No new request.
5. **The header says where the book stands against Wealthsimple,** in one of three states: `Matches Wealthsimple as of Oct 20`, `Checking against Wealthsimple`, or `Not yet checked against Wealthsimple`. A difference is named with both figures, as today. This is the positive, dated state every reconciling app shows (YNAB, Quicken, Beancount, §5).
6. **Every reader and writer of the earlier app's file is deleted in the same release,** with #575's and #586's pull machinery and the pull's own import-replacing code. About 25,700 lines go; about 300 hand-written lines come in.
7. **One release later,** the 37 migrations and their 36 schema snapshots are folded into one base schema, and the migration's own code leaves with them. A book from before that release is refused with one sentence: open it with 2.10.0 first. This is the pattern Django, Rails and GitLab document (§6).

Nothing runs at every start. Nothing waits on a condition. Nothing of the earlier app remains in code that runs, in the book, or in the data folder's use, with three things named so you know them: the first event of the orders and brackets you placed before the Rust app stays in the order log as your own history (§3); the old model crate, which the live wire types still reference, is its own plan (§12); and the names `.bagholder-rust` and `-rust-` in the archive are left alone because the updater finds releases by them (§12).

## 2. What happens to your book, step by step

Your book today holds 6,156 import rows, by the CTO's read-only count of 2026-10-21: 5,867 superseded, 288 removed, 1 live (so 5,868 rows ever counted, of which one still does; plan #573's count of 2026-10-20 was 5,573 superseded, before the last syncs). A superseded or removed row has no transactions, because the book deletes them before it marks a record superseded or removed (`rust/crates/book/src/records.rs:502-507`, called at `links.rs:93` and `records.rs:486`), so those 6,155 rows count in no figure now. No writer in the current code can anchor a trade on such a row: supersede moves or orphans every anchored trade first (`links.rs:58-74`), removal orphans them first (`records.rs:478-480`), and a trade can only be opened on a transaction that exists (`trades.rs:59-61`). The one live row books the leaving side of the 2025-06-16 move, a transfer out, on which the engine opens no trade.

## 4. The pull: one rule, and what is reverted

**The rule.** For every account the broker states, open or closed: read its activity from its last complete read, lowered to the first day of any row of it stored before it was final (`pull.rs:215-222`, the only lowering left), whole where it has no complete read. The `closed`/`to_read` split, `closed_read`, `since` and `closed_due` go (`pull.rs:183-209`, `:220-221`, `:565-598`). Today the balances and statements are read only for open accounts (`pull.rs:365`, `stated.iter().filter(|a| a.open)`; `:377-384`); after this they are read for every account Wealthsimple lists, closed ones included. The book's account status follows the broker's on every pull: today it is written only when the account is added (`pull.rs:125-126`, `rust/crates/book/src/identity.rs:86-88`, and no `UPDATE accounts` sets it anywhere), while the five-minute balances pass keys off it (`pull.rs:909-911`), so an account the broker reopened would never be re-read. One update where it differs.

**A closed account's statement.** Wealthsimple's `closed` is stored as a cash statement of nothing (`Book::store_cash`, `rust/crates/book/src/statements.rs:286-296`, with an empty map) and a units statement of nothing (`store_units`, `:513-525`, once as of the pull's day when first stated closed), by the sync and by the five-minute balances pass (`pull.rs:905-913`, which today skips every account the book holds as not open). The second matters: a cash difference is said only once a balance stated after the activity read confirms it (`equity.rs:159-166`, `status.rs:213`), and the sync stamps its statement and its read with the same instant (`pull.rs:226`, `:352`, `:1055`), so a statement stored only by the sync would leave a closed account's difference pending forever, which is why the page is silent about closed accounts today. The units check runs once a units statement exists, an empty one included (`equity.rs:179`; `rust/crates/server/src/engine_inputs.rs:243`). This follows what the statements module already assumes of a closed account (`rust/crates/broker/src/statements.rs:921-926`, the code at `:931`). No request; one read-only probe of `FetchAccountsWithBalance` for a closed id is not built (no recorded reply holds a closed account; risk, §8).

**Accounts the import pooled.** The import put several Wealthsimple ids into one book account where the earlier app counted them as one and the broker types them alike (`rust/crates/book/src/import/mod.rs:205-258`); the pull carries that case as "one book account can be several of the broker's" (`pull.rs:361-362`, `:375-377`). The counting query's fifth line says whether your book has any. If it does, they are split back to one book account per Wealthsimple id, as the broker states them, in a small plan of its own right after 2.10.0: it moves history between accounts and needs its own tests. If it does not, the pooling code is deleted as dead in PR 2.

**The rule's stated limit.** Wealthsimple's feed is asked by `startDate` (`client.rs:235-241`), and nothing in the repository says whether Wealthsimple applies it to a row's `occurredAt` or to when the row was posted. Under the code's own reading, a row Wealthsimple adds later under an older date, in any account, is not asked for by an incremental read. Every vendor that documents this says a date window is not enough: Plaid, "a removed transaction will no longer appear in /transactions/get" and "a posted transaction cannot necessarily be considered immutable"; Teller, "When a pending transaction posts, its date often changes to the posting date"; Akahu, "banks often mutate a transaction in the days (or weeks) following its posting" (§11). Wealthsimple offers no cursor. So the catch is where bank reconciliation puts it: the balances. A cash difference is confirmed by the next balance and said; a units difference is said as of the day read; the monthly statements are read for any account whose cash differs, and the movements the feed left out are booked from them (`rust/crates/broker/src/statements.rs:1-20`). The person's way to read everything again is the one the app has: `Clear data` → `Wealthsimple records`, journal kept (`SPEC.md` pages-24). No re-read driven by a reason is added: of such a rule you said "That is not a fix".

## 5. How you are assured the numbers are right, on the page

What exists: after every change to the figures, the engine compares each account's cash per currency with the cash Wealthsimple stated, and its units with Wealthsimple's units as of the day of the last full read (`rust/crates/engine/src/equity.rs:130-214`); a confirmed difference is said in the header with the account and both figures (`rust/crates/server/src/status.rs:201-237`, pending ones dropped at `:213`), as is a month whose statement does not reconcile, and every sale beyond what was held. What is missing is the positive half: today the header's line has four outcomes, the sync step, an error, `Not connected`, or `Synced 2 min ago` (`web/src/App.svelte:306-314`), a time, never that the figures agree.

The practice in the category is a positive, dated state. YNAB: reconciled transactions "are locked and marked with a lock icon", and reconciling "provides assurance that the numbers in your plan are correct". Quicken marks a reconciled transaction with an `R`. Beancount keeps a dated balance assertion in the ledger and "will report an error" on any departure. The accounting term is a bank reconciliation: once prepared, "both the bank balance and the company balance will be the same amount" (§11).

**The rule** (`SPEC.md` §4, beside pages-13): when no failure stands, the sync line also says where the book stands, worked out when the header is read from the checks the engine already made and the stamps the book already keeps (`rust/crates/engine/src/input.rs:777-796`), with no new stored state:
- `Synced 2 min ago · Matches Wealthsimple as of Oct 20`: every stated account's cash in every currency and every holding's units equal what Wealthsimple states, nothing pending. The day is the earliest day any account's units are stated as of.
- `Synced 2 min ago · Checking against Wealthsimple`: Wealthsimple has stated a balance more recently than the app last read that account's activity, or a difference waits for the balance that confirms it, so the app waits for the next read before saying the two agree or differ (`BrokerCheck.pending`, `equity.rs:117-125`; `Difference::pending`, `:109-113`).
- `Not yet checked against Wealthsimple`: no account has a statement at its last full read.
A standing difference is said in red with both figures and takes the line, as today. Nothing appears and then goes (`SPEC.md` pages-8; the engine's own rule at `equity.rs:160-163`).

Built as one field on `Status` (`status.rs:19-55`, built at `:142-180`), computed beside `broker_failures` (`:136`), about 40 lines; the generated type (`web/src/lib/generated/status.ts:43`) and six lines in `syncLine()`. The server already works out, after every change, whether each account's cash and holdings equal Wealthsimple's; this adds one word to what it sends the page saying so, and the page prints it. Nothing new is asked of Wealthsimple.

## 10. The counting query (optional, read-only)

On a copy of your book (`cp ~/.bagholder-rust/book.db /tmp/book-copy.db`), `sqlite3 -readonly /tmp/book-copy.db` and paste. It prints states and counts only.

```sql
SELECT 'import records', state, COUNT(*) FROM source_records WHERE source = 'bagholder-import' GROUP BY state;
SELECT 'trades anchored on an import record', r.state, COUNT(*) FROM trades t JOIN source_records r ON r.id = t.anchor_record WHERE r.source = 'bagholder-import' GROUP BY r.state;
SELECT 'notes on those trades', COUNT(*) FROM journal j JOIN trades t ON t.id = j.trade_id JOIN source_records r ON r.id = t.anchor_record WHERE r.source = 'bagholder-import';
SELECT 'orphaned trades with a note', COUNT(*) FROM journal j JOIN trades t ON t.id = j.trade_id WHERE t.anchor_record IS NULL;
SELECT 'book accounts holding more than one Wealthsimple id', COUNT(*) FROM (SELECT account_id FROM account_refs GROUP BY account_id HAVING COUNT(*) > 1);
SELECT 'orders and brackets carried from the earlier app', (SELECT COUNT(*) FROM order_events WHERE kind = 'imported') + (SELECT COUNT(*) FROM bracket_events WHERE kind = 'imported');
```

Expected: the first line's three states; zero on the second and third; the fifth and sixth tell us about §4's pooled accounts and §3's order events. If the second is not zero, the migration orphans those trades with their notes kept, says how many in the log, and the sync creates the trade afresh from Wealthsimple's row without the note. The note stays in the book.
