## 0. Why

2.10.0 shipped on generated books and planted faults, which prove that code does what it says, and broke a real book, because the broker's real feed has shapes the repository's made-up Wealthsimple never states: a move listed by its arrival alone, an account under two ids the broker links as one, a conversion whose paid side only the statements settle, a row listed in a closed account after it closed. Every one of those shapes was already known to the code (rule 13, now rule 15: `mapping.rs:96-99`, `fn leaving` at `:1023`; `read_beside`, `adapter.rs:521`; the statements walk, `broker/src/statements.rs:14-19`; `store_account_links`, `book/src/statements.rs:183`) and to the pull tests, which build their books from the recorded replies (one account, 53 transactions) and edit them by hand into each shape (`tests/pull.rs:329-384`, `:402-460`, `:688-703`). None was in the stand-in the capacity job and `tests/generated.rs` build whole books from (`rust/crates/wealthsimple/src/generated.rs`), so a change to how the book is built from the feed could pass every test and be wrong on every real book. The owner will not run checks on their machine, rightly: the repository has every line of code, and the proof belongs in it.

## 1. The design

**The made-up Wealthsimple states every shape the pull reads.** `Generated` plans a book's activity (`generated.rs:203-230`, `Plan`) and answers each request with a recorded reply of the real shape, its fields set (`:1-7`). It gains the shapes below. `Size` has no place for a shape today (`:24-41`), so they are a set of names beside it, each off by default and switched on by name: a test says which shapes its book has, `REFERENCE` (`capacity.rs:69`) keeps its meaning, and a pull change names the shape it touches.

| Shape | What the real feed does | Where its form is established, without the owner | Today |
|---|---|---|---|
| A move listed by its arrival alone | the arriving row names `opposingAccountId`; the other account's feed never lists a leaving row | the stand-in's own template holds both halves of a real move, `edited-activity-one-per-kind.json` edges 91 (`DESTINATION`) and 100 (`SOURCE`); rule 15's doc (`mapping.rs:1011-1022`) | both legs always emitted (`generated.rs:850-853`, `:875-876`); hand-edited in one helper, `resp_rows` (`tests/pull.rs:370-384`), used by five tests |
| An account under two ids the broker links | the old id `closed`, the new `open`, each naming the other as `linkedAccount` | `edited-accounts-one.json` (the stand-in's account template) carries `status` and `linkedAccount: null`; the reader reads `status` and `linkedAccount.id` only (`read.rs:65-72`) | every account `open`, no link (`generated.rs:1112-1140`); hand-edited in `link_resp` (`tests/pull.rs:690-703`), three tests |
| A closed account with history | `status: closed`, its activity ending, its positions empty | the same template, its value set as `resp_replies_with("closed")` does (`tests/pull.rs:336-362`); its rows are edges 12-19 of the activity template | none in the stand-in; hand-edited |
| A row listed in a closed account after its one full read | a `SOURCE` row dated after the account's last full read, in an account the pull reads no more (`pull.rs:189-196`) | edge 100's kind, dated between two pulls | the `LateMove` fixtures (`tests/pull.rs:406-460`), hand-edited |
| A conversion whose paid side the feed leaves unstated | `FUNDS_CONVERSION` whose detail is a funding intent stating only the side received (`mapping.rs:761-771`, `conversion-side-unstated`); the paid side settled from the statements (`statements.rs:103-107`, `Paid`) | `FetchFundingIntent-1.json`, recorded | the stand-in answers every conversion with `FetchInternalTransfer-1.json`'s form, whose `amount` states the paid side, so its conversions are two-sided (`generated.rs:735-752`, `mapping.rs:772-780`) |
| Statements across months, with closing balances | `FetchMonthlyStatementWithTransactions` per id per month, each currency's rows in their own list with a running `balance`, the closing balance the last row's (`statements.rs:922-923`); a conversion appears as an `FXCONVERSION` row on each currency's side | the document's fields (`graphql/FetchMonthlyStatementWithTransactions.graphql:29-55`); the one recorded month `wealthsimple-statements/lira-2025-06.json` carries every field a row needs; the `FXCONVERSION` row's code and description form, `Convert CAD (executed at …) - $1USD = $1.35CAD`, in `broker/src/codes.rs:97-98` | `Generated::statement` answers `Ok(None)` (`:1259-1263`); no statement template (`:321-386`); one month recorded, of one account |

Each shape is set on a recorded reply the stand-in already includes, as every reply is; the statement is the one new template, an `include_str!` of the recorded month with its rows regenerated per account per month. Nothing is captured from anyone's account, and no new page is recorded.

**One test per shape over the stand-in,** in `rust/crates/wealthsimple/tests/pull.rs`, the pull run against `Wealthsimple::new(Generated::new(..))` as the capacity job runs it (`capacity.rs:453`), each holding the figure the shape must produce: the leaving leg booked once; one book account per linked set, open while either id is; the closed account read whole once and its late row booked once from its own row; the conversion's paid side booked from the statement and the month reconciling; the closing balances agreeing with the book's cash. The hand-edited fixtures those tests use today (about 130 lines) stay as the recorded evidence of each shape (decided at PR 1's review); the recorded replies stay as the templates they are.

**A rebuild test over the shaped book,** in the same tests: the book built from the stand-in with every shape on, its figures taken (each account's cash per currency and units per listing from the transactions, as `cash_by_account` takes them, `tests/pull.rs:390-400`), then read whole again from the same stand-in (its activity reads cleared, as migration 37 cleared them) and the figures and the records' states equal. A re-read of the feed must give the same book; 2.10.0's did not, and this is the test that would have failed. Every migration that changes records or accounts takes its before-state from the shaped book's rows copied into a file at the version before, as `as_v36` copies them (`book/tests/schema.rs:396`), beside the per-migration tests already there (37 at `:466`, 39 at `:547`, 40 at `:620`), each difference in figures named as the migration's intended effect.

**The capacity job builds its reference books with every shape on,** so the budget is measured on a book with the feed's real shapes, not a smooth one (`rust/crates/server/src/capacity.rs`).

**The rule, in `docs/architecture.md` §16 beside the cost budget:** a change to how the book is built from the broker names the shapes it touches, and the stand-in states them; a shape the real feed turns out to have that the stand-in lacks is added to the stand-in first, from the recorded reply of its kind, and the change follows.

## 2. What it costs

About 400 lines in `generated.rs` (six shapes, their switches, the statement template and answer) on its 1268; about 300 lines of tests replacing about 130 of hand-edited fixtures; about 120 lines for the rebuild test and the copied before-states, on scaffolding `book/tests/schema.rs` already holds. No new recorded page. No runtime cost: the stand-in exists only in tests and the capacity job.

## 3. Order

1. The shapes in the stand-in, with the per-shape tests, one PR. The set is complete when each row of the table has its test.
2. The rebuild test and the migrations' before-states from the shaped book, one PR.
3. The capacity job on the shaped books, one PR, with the table re-measured.

Nothing else changes in the app. A pull change after this is accepted only with the shape it touches named and tested; a pull change before PR 1 is not accepted.

## 4. Not included

- Any capture from a person's account, any step on a person's machine, any shipped command, any visible change.
- An account the broker no longer lists: the pull has no rule for one (`unlisted`, `pull.rs:551-560`, is about rows) and the feed is not known to do it; nothing is stated on a guess.
- The closed-account rule of 2026-10-21 (every account read the same way): it stays withdrawn at the owner's word of 2026-10-24; if it is ever reconsidered, the shapes here are what prove it.
- A trade orphaned by a record's removal re-attached on its restore (a schema change; noted at #610).
