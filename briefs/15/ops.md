## findings

### ops-A-1 [high/design] A headless copy cannot be reached from another device, and if it is, there is no sign-in in front of orders
- status: confirmed — code: confirmed | std: confirmed
- standard: Self-hosted finance apps ship an authenticated front door and document the reverse-proxy path: Ghostfolio (user login, `ROOT_URL`), Firefly III (login, `APP_URL`, trusted proxies), Actual Budget (server password), Jupyter (a per-instance token printed at start, the model brief 10 recommended). A Host-header allowlist is a DNS-rebinding guard, not access control; the team's own docs/architecture.md §12 says remote access goes through a proxy the person trusts and every write carries a token. docs/old-app-mistakes.md:63 already names 'with the container's port published beyond loopback, anyone on the network can place orders' as not guarded.
- observed: The gate admits only requests whose Host header is exactly `127.0.0.1:<port>` (`host_ok`), so `http://pi.local:8765` or `http://192.168.1.10:8765` from a laptop is 403 even after the port is published; when the server is bound beyond loopback (the image sets BAGHOLDER_BIND=0.0.0.0) `peer_ok` admits every peer. There is no password, token or session of the app's own; the only write check is a static `x-bagholder` header or `Sec-Fetch-Site: same-origin`. The README's Docker section says 'a machine you keep on' and 'published on the host's loopback only' and never says how to open it from another device (an SSH tunnel, or a proxy that rewrites Host to 127.0.0.1:8765). The owner states headless deployments favour Docker.
- evidence: rust/crates/server/src/http/mod.rs:320 (host_ok: the name must be 127.0.0.1 even when bound elsewhere; any other Host is refused); rust/crates/server/src/http/mod.rs:309 (peer_ok returns true for every peer once bind_host is not 127.0.0.1); rust/crates/server/src/http/mod.rs:301 (a write is 'from the page' on a static header name, not a secret); rust/Dockerfile:43 (BAGHOLDER_BIND=0.0.0.0 inside the image); docker-compose.yml:12 (published on 127.0.0.1 only; nothing for a LAN/headless reader); README.md:145 ('Open http://127.0.0.1:8765': no route to a headless machine is documented)
- impact: The advertised headless/Pi deployment either cannot be used (403 from any other device) or, after the person publishes the port or fronts it with a proxy that rewrites Host, exposes an order ticket that places real trades and a Wealthsimple session to anyone who reaches the port, with no sign-in. Measured: `Host: pi.local:8811` and `Host: localhost:8811` both answer 403.
- proposal: Ship the access layer the architecture already describes: a per-install secret (printed at start and settable by env, as Jupyter does) that a browser presents once and keeps as an HttpOnly cookie; a `BAGHOLDER_PUBLIC_URL`/trusted-proxy setting that admits that Host; write protection tied to the cookie plus the custom header. Loopback desktop copies can auto-admit the local page so nothing changes there. Document the two supported remote paths in README (SSH tunnel; reverse proxy with the setting).
- ux-conflict: True — A sign-in step appears for anyone reaching a copy from another device; the loopback desktop copy can stay password-free.
- owner decision: 2026-09-25 'AI agents reach the app through its MCP tools only… no tokens with access classes; the Host/Origin check and the page's write token stay'; 2026-09-26 access work (remote-access key) moved out of the migration.
- confidence: high

### ops-A-3 [high/robustness] An update that fails rolls the binary back but not the migrated stores, so the restored version refuses to start and the app is down
- status: confirmed — code: confirmed | std: confirmed
- standard: An updater that can roll back restores the state the previous version can run on: Home Assistant takes a backup before an update and offers it on failure; Sparkle/Tauri updaters leave data untouched because their apps do not migrate on launch; the team's own docs/architecture.md:102 and :220 promise 'an update that is rolled back restores that snapshot'. Trading platforms also refuse to restart while an order action is in flight (IBKR TWS warns of pending orders on exit).
- observed: The supervisor's rollback (`restore_previous` → `rollback_in`) copies only the kept executables back. The stores are migrated on the new version's first start and a snapshot is taken (`migrate.rs`), but nothing restores it; the old binary then hits `MigrateError::Newer` ('written by a newer version'), `serve()` returns 1 before binding, the supervisor returns 1, and the only word is on stderr. `start_update` refuses only while a sync runs; an order or bracket action in flight is not waited for, and `request_restart` stops the server 500 ms after install. The 20-second health window means a crash in the first sync minutes later is never rolled back.
- evidence: rust/crates/server/src/update.rs:575 (restore_previous: git reset and the kept files, nothing of the stores); rust/crates/server/src/update.rs:593 (rollback_in copies HOME/previous over the executables only); rust/crates/sqlite/src/migrate.rs:165 (a file at a newer schema is refused); rust/crates/sqlite/src/migrate.rs:227 (the pre-migration snapshot (VACUUM INTO) exists but is not used by the rollback); rust/crates/server/src/main.rs:141 (Figures::open failing returns 1 before the port is bound); rust/crates/server/src/update.rs:743 (start_update checks only st.syncing)
- impact: The exact scenario the rollback exists for (a release with a schema migration whose server dies in its first 20 s) ends with no running copy: a systemd copy loops to its start-limit and stops, a launchd copy stays dead, and the person sees 'connection refused' with the reason only on a stderr nobody captures. A stop or target the watched bracket was sending at that moment is interrupted mid-request.
- proposal: On rollback, restore each store's newest snapshot stamped by that update's migration (they are already taken and named), then start the previous binary; if a snapshot is missing, do not roll the binary back — leave the new one and say why on the page. Have `start_update` wait for `gate` to report no bracket or order in flight (the state the app already tracks), as the architecture says. Surface the failure on a page served by the supervisor or the restarted server rather than stderr.
- ux-conflict: False 
- owner decision: 2026-09-26 'the running work (crash restart, safer updates, signed releases…)' is out of the migration.
- confidence: high

BAGHOLDER_LOG_REQUESTS is undocumented; a SIGTERM stop logs nothing.
