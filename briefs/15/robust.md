## findings

### robust-A-1 [critical/design] A bracket stopped by the order cap can be left with no stop at Wealthsimple and no stop watched here
- status: confirmed — code: confirmed | std: corrected (The code does what the finding says: `decide` returns nothing in Halted before stop_hit is computed (core/src/bracket.rs:637), `quotes_for` skips Halted brackets (server/src/orders/brackets.rs:345), and the test asserts )
- standard: An automation guard rejects new order flow and leaves resting protective orders in place (IBKR precautionary settings reject the offending order, https://www.interactivebrokers.com/en/software/tws/usersguidebook/configuretws/precautionarysettings.htm); brokers with native trailing stops (IBKR, Questrade) move the level server-side, never as a cancel-then-replace pair with an unprotected gap. The owner's own SPEC.md:370: 'one more stops it: it sends nothing further, its stop level is watched here'.
- observed: The cap (gate.rs:83-95) counts every exit row written and every cancel asked in the last 60 s, and refuses the request that would be the eleventh, whether a cancel (gate.rs:141-143) or a place (gate.rs:106-107). A trail move is a cancel then a place, so on a fast mover the eleventh request can be the place that follows a confirmed cancel; `held_back` then records `Halted` with `exit: None` (brackets.rs:225-229, bracket.rs:414-420). In Halted, `decide` returns before `stop_hit` is computed (bracket.rs:637), so the watched market sell can never fire, and `quotes_for` fetches no quote for a halted bracket (brackets.rs:345). The test (tests_execution.rs:788-814) asserts only that `creates.len()` is unchanged, never that a bid through the level sells.
- evidence: rust/crates/core/src/bracket.rs:637 (`if b.phase == Halted { return Step::nothing(); }` before stop_hit is computed); rust/crates/server/src/orders/brackets.rs:345 (quotes_for excludes Halted: no tape for a halted bracket); rust/crates/server/src/orders/gate.rs:106 (the cap trips at a place as readily as at a cancel; a place after a confirmed cancel leave); SPEC.md:370 ('its stop level is watched here' while stopped: not built); rust/crates/server/src/tests_execution.rs:812 (asserts creates unchanged, not that the level is watched)
- impact: The scenario the guard exists for (a fast trail on a strong mover) can end with the position unprotected until the person notices a header line and edits the bracket; a reversal after the run-up sells nothing.
- proposal: Count the cap before a cancel only, so the guard never removes a resting stop; in Halted keep fetching the quote and let `decide` fire the watched market sell (suspend only trail moves and target swaps). Rate-limit trail re-placement itself (one move per N seconds, or only on a full step) rather than halting, since a fast mover is not a fault. Add the test: halted with no resting exit, bid through the level, a market sell goes out.
- ux-conflict: False 
- owner decision: No guard against a single far-off quote, and no global switch for automated orders (2026-09-26): the per-bracket cap is the owner's chosen guard; the proposal keeps the cap and fixes what it does.
- confidence: high

### robust-A-2 [critical/robustness] A crash or kill during a ticket Sell leaves the bracket in `closing-for-sale` forever: stop cancelled, nothing sold, nothing watched
- status: confirmed — code: confirmed | std: confirmed
- standard: An order system recovers every in-progress workflow on restart from its persisted state (FIX session recovery: every pending state has a defined resolution after reconnect; IBKR reconciles open orders on reconnect via reqOpenOrders). A protective-order swap is designed so that an interruption at any point leaves either the old order or a watcher in place.
- observed: `sell()` records `SaleAsked` (phase → ClosingForSale), cancels the exit, then waits up to 30 s in the HTTP handler; only that same call ever records `SaleDropped` or `Sold` (server/src/orders/ticket.rs:876-940). If the process dies (SIGKILL, power loss, an update restart mid-wait) after the cancel is confirmed, on restart `decide` in ClosingForSale does nothing when no exit is in flight (core/src/bracket.rs:748), never checks the stop level, and no code path re-enters the phase: `adjust` refuses it (edit.rs:122), `guarding()` skips it for a new sale, `closed_elsewhere` is skipped for it (bracket.rs:646). The panel reads `Cancelling` (doc.rs:291). Only a clean stop (`app.wait` returning true) drops the sale.
- evidence: rust/crates/server/src/orders/ticket.rs:876 (SaleAsked recorded; recovery events only from this function's own later lines); rust/crates/core/src/bracket.rs:748 (ClosingForSale: `Some(x) if in_flight => keep_cancelling, _ => nothing` — no stop_hit, no ); rust/crates/server/src/orders/edit.rs:122 (a ClosingForSale bracket cannot be adjusted); rust/crates/server/src/orders/doc.rs:291 (the leg shows 'Cancelling' indefinitely); SPEC.md:373 ('the position is never left with neither the stop nor the sale' — broken across a restart)
- impact: After a crash in a 30–60 s window the person's position has no stop at Wealthsimple, no watcher, and a panel that says the exit is being cancelled.
- proposal: Make the sale a persisted phase with its own recovery: on start (and on every check) a ClosingForSale bracket whose sale order does not exist in the book, or whose `SaleAsked` is older than CANCEL_CONFIRM_SECONDS, records `SaleDropped` and returns to Guarding (its stop re-placed by the next step); in ClosingForSale still fire the watched market sell on stop_hit. Add a fake-broker test that kills the process between the confirmed cancel and the send and asserts the stop is back after restart.
- ux-conflict: False 
- owner decision: -
- confidence: high

### robust-A-3 [high/robustness] A cancel whose answer was lost is never asked again: `cancelling` is a state nothing can leave
- status: confirmed — code: confirmed | std: confirmed
- standard: FIX Order State Changes: a pending cancel 'DOES NOT INDICATE THAT THE ORDER HAS BEEN CANCELED'; the buy-side follows an unanswered cancel with an OrderStatusRequest and re-issues the cancel when the report shows the order still working with no cancel pending (scenarios G.1, C.1.a). IBKR's `PendingCancel` resolves to `Cancelled` or back to `Submitted`; a cancel can be re-sent safely.
- observed: `gate::cancel` records `CancelAsked` before the send and treats `Sent::Unclear` (timeout, 5xx, unreadable) as 'still being cancelled; the read-back settles it' (gate.rs:150). But the read-back maps both a plain working order and `CANCEL_PENDING` to `BrokerStatus::Open` (gate.rs:336), and the fold keeps `Cancelling` on Open (order.rs:413). No code re-sends a cancel while the order is `Cancelling` (`keep_cancelling`, bracket.rs:776, does nothing in that state). So a cancel that never reached Wealthsimple leaves: a `ToTarget` bracket that never places its target; a `Closing` bracket never `Done`; a person's `cancel_order` answered 'cancelling' forever with the order still resting.
- evidence: rust/crates/server/src/orders/gate.rs:150 (Unclear cancel answer: nothing recorded, no retry scheduled); rust/crates/server/src/orders/gate.rs:336 (CANCEL_PENDING → Open: the read-back cannot tell 'cancel pending' from 'working, no cancel); rust/crates/core/src/order.rs:413 ((Cancelling, Open) stays Cancelling on every read); rust/crates/core/src/bracket.rs:776 (keep_cancelling sends nothing once the state is Cancelling)
- impact: A single dropped HTTP answer on a cancel freezes a bracket's swap or its ending until the person cancels the whole bracket by hand; the Orders panel says 'Cancelling' with no end.
- proposal: Read `CANCEL_PENDING` as its own status; when an order is `Cancelling` and a read-back says plainly working (not cancel-pending) after the cancel's own rest (e.g. 30 s), re-send the cancel through the gate (cancels are idempotent at every broker; a cancel of a gone order is a harmless reject). Cap the re-sends under the existing per-bracket cap and say 'Cancel not confirmed' on the leg.
- ux-conflict: False 
- owner decision: -
- confidence: high

### robust-A-4 [high/robustness] 'No such order' on the first read after an unclear send is final: the order is Failed, never re-read, and a bracket places its exit again
- status: confirmed — code: corrected (The mechanism is confirmed; the plan citation is at docs/plans/stage-4-execution.md:43, not :90, and B-3's consequence (a bracket entry marked Failed never arms) belongs to the same root cause and is folded in here.) | std: confirmed
- standard: After a lost acknowledgement the safe sequence is a status request over an acknowledgement window, and only a definitive 'unknown order' after that window allows a replacement (FIX Order State Changes scenario G.1; IBKR keeps an order PendingSubmit until acknowledged or rejected; Alpaca keys on client_order_id and answers 422 on a duplicate so a resend cannot double).
- observed: A create that answers Unclear (timeout, 5xx, non-JSON: ws/src/session.rs:730-741) leaves the order Unconfirmed; the ticket calls ask_read at once (ticket.rs:836) and the next bracket check reads the exit back (brackets.rs:263). A single Found::None is recorded as NotFound (gate.rs:171) and (Sending|Unconfirmed, NotFound) is Failed, a final state, with no minimum number of reads or elapsed time (order.rs:382-388). The Sending guard covers only the create call itself (gate.rs:118-129), so an order left Sending by a crash is read back on the first refresh_orders after restart (readback.rs:425-436) and failed the same way. reconcile clears a Failed exit (bracket.rs:815-826) and place() goes out again at once because Placed reset attempts to 0 (bracket.rs:348, 601-604). A Failed order is no longer in flight, so it is never read again, and a bracket whose entry was so marked never arms (arm(), bracket.rs:784-792). Whether Wealthsimple's read by external id can lag its accept is undocumented; the plan says a duplicate external id is 'not relied on' (docs/plans/stage-4-execution.md:43), so nothing stops two exits resting for the same shares.
- evidence: rust/crates/server/src/orders/gate.rs:171 (a None from the read is recorded as NotFound with no second look); rust/crates/core/src/order.rs:384 (Sending|Unconfirmed + NotFound → Failed immediately); rust/crates/core/src/bracket.rs:601 (place() after a Failed exit: attempts is 0 (reset by the earlier Placed), so it goes out a); rust/crates/server/src/orders/readback.rs:425 (only orders_in_flight are read back; an order failed this way is never re-read); docs/plans/stage-4-execution.md:43 ('Whether Wealthsimple refuses a repeated external id is not documented and is not relied o)
- impact: A timeout on a send followed by a lagging index yields two resting sells on one position, or a live order (and its fills) at the broker that the book calls Failed and stops watching; a bracket built on such an entry never guards. The sweep cancels an orphan exit later, but not before it can fill.
- proposal: Give NotFound a grace: an order sent within the last N seconds, or Sending at restart, that reads not-found is recorded as such and re-read K times over the acknowledgement window (and checked against the pending-order feed) before it is folded to Failed; only then may the bracket place again. Record in the broker capabilities whether a duplicate external id is refused and test the gate against the fake with both settings.
- ux-conflict: False 
- owner decision: -
- confidence: medium

### robust-A-5 [high/robustness] POST /api/order has no idempotency key: two identical submissions are two orders
- status: confirmed — code: confirmed | std: confirmed
- standard: The client assigns the order id (FIX ClOrdID is set by the initiator; Alpaca `client_order_id` rejects a duplicate with 422; Stripe's Idempotency-Key). Brokers' tickets disable resubmission and dedupe on the client id so a retried request cannot double an order.
- observed: The external id is minted server-side per request (ticket.rs:700) and nothing in the body identifies the attempt. Measured on the dry demo: two identical POSTs returned two ids and wrote two orders. The page's only guard is a `busy` flag (web/src/lib/ticket/ticket.svelte.ts:275); its fetch has no timeout and a transport error is shown as `submitError`, inviting a resubmit while the first request (up to the 90 s mutation timeout, ws/src/session.rs:717) may still place.
- evidence: rust/crates/server/src/orders/ticket.rs:700 (`let id = format!("order-{}", uuid4())` per request); web/src/lib/ticket/ticket.svelte.ts:275 (busy flag only; a failed fetch shows an error and lets the person submit again); rust/crates/server/src/http/orders.rs:21 (the route has no dedupe)
- impact: A flaky hop between page and server (a tunnel, a Docker bridge, a sleeping tab) turns one intended order into two.
- proposal: Let the page mint the external id when the Review step opens and send it in the body; the server writes the order under that id and answers the same result for a repeat (unique key on `orders.id` already exists). Keep the busy flag; show 'Sent, not confirmed' rather than an error when the answer is lost.
- ux-conflict: False 
- owner decision: -
- confidence: high

### robust-A-6 [high/narrow-fix] A refused stop placement's back-off also delays the emergency market sell
- status: confirmed — code: confirmed | std: confirmed
- standard: A stop-order retry schedule and a protective market exit are separate concerns; broker apps and OMSs never hold a stop-triggered market sell behind an unrelated rejection's back-off. SEC 15c3-5's price/size controls apply to new order flow, not to a liquidation the strategy has already decided.
- observed: `place()` gates every role on `may_retry` (bracket.rs:601-604) and `Refused` increments `attempts` whatever role was refused. After a stop placement is refused (any reason: a gap-down puts the stop above the market, a close-hours refusal, a transient error), the watched market sell on `stop_hit` (bracket.rs:668, 702, 713, 742) waits 60 s, then 5, 15 and 60 minutes — while the bid is through the level. `RETRY_SECONDS` (bracket.rs:111) implements SPEC.md:375 for 'an exit Wealthsimple rejects', which did not consider the market sell sharing the counter.
- evidence: rust/crates/core/src/bracket.rs:602 (`if !b.may_retry(now) { return Step::nothing(); }` for Stop, Target and Market alike); rust/crates/core/src/bracket.rs:668 (Guarding, no exit, stop hit → place(Market) still goes through may_retry); rust/crates/core/src/bracket.rs:111 (60/300/900/3600 s rests)
- impact: Exactly when a stop cannot rest (price already through it), the sell that replaces it is delayed by up to an hour.
- proposal: Keep per-role attempt counters, and exempt the market sell on a hit level from the schedule except for a short rest after its own refusal (e.g. the 5-second check). Add the case to `core/tests/brackets.rs`: stop refused, bid below the level → market sell on the next check.
- ux-conflict: False 
- owner decision: -
- confidence: high

### robust-A-7 [high/performance] One slow Wealthsimple call stalls every other bracket's watch for up to 90 seconds
- status: confirmed — code: confirmed | std: confirmed
- standard: An order engine never blocks its market-data/decision loop on a network send: sends are asynchronous with their own timeouts and the watch loop keeps running (any OMS/EMS; IBKR's TWS API is fully asynchronous). A 5-second protective check must be independent of a 90-second HTTP timeout.
- observed: `bracket_tick` checks brackets one after another (brackets.rs:388); inside a check, a place or cancel goes to `Client::mutate` with a 90 s timeout (ws/src/session.rs:717), and a read-back to `graphql` with 90 s (ws/src/session.rs:647). One hung call therefore suspends the other brackets' stop watch (and the sweep) for up to 90 s, eighteen missed checks. The ticket's `sell()` adds a 30 s + 30 s wait inside an HTTP handler (ticket.rs:766, 906).
- evidence: rust/crates/server/src/orders/brackets.rs:388 (sequential `for sb in &live { check_bracket(...) }`); rust/crates/ws/src/session.rs:717 (request_once with Duration::from_secs(90) inside the check); rust/crates/ws/src/session.rs:647 (read-back POST with a 90 s timeout)
- impact: A single stuck request leaves every other watched stop blind during the very volatility that produces stuck requests.
- proposal: Run each bracket's check on its own task with the bracket lock, or move sends to a worker so the decision loop only records 'sending' and moves on; cut the order-path timeout to something a person would wait (10–15 s) since anything longer is settled by read-back anyway.
- ux-conflict: False 
- owner decision: -
- confidence: high

### robust-A-8 [high/operations] Headless deployments have no channel for a fill, a stop-out or a halted bracket
- status: confirmed — code: confirmed | std: confirmed
- standard: Every broker app pushes fills and rejections to the phone (Wealthsimple, IBKR Mobile, Questrade); self-hosted services that act unattended offer at least one remote channel (email, ntfy/Pushover push, a webhook) — Grafana alerting, Home Assistant, Uptime Kuma all do.

The owner states headless deployments favour Docker, i.e. exactly the case with no desktop and usually no open page.

- impact: An automated market sell, a rejected exit or a halted bracket on a Pi or in a container reaches nobody until they next open the page.
- proposal: Add one remote channel behind the existing notification settings — a webhook/ntfy URL or SMTP — used whenever no native channel exists (and optionally always for the 'fills' and 'problems' kinds); test-notification already exists to verify it.
- ux-conflict: False

- confidence: high

### robust-A-9 [high/design] The 'write token' is any non-empty header: beyond loopback, anyone on the network can place orders
- status: confirmed — code: confirmed | std: confirmed
- standard: A state-changing endpoint carries a secret the browser page obtains from the server (a CSRF token or a per-install key), not a static header name; OWASP CSRF guidance; every broker API requires a credential per request.
- observed: `admitted` accepts a POST when `Sec-Fetch-Site: same-origin` or `X-Bagholder` is non-empty (http/mod.rs:301); the page sends `X-Bagholder: 1` (web/src/lib/api.ts:65). When the server is bound beyond loopback (a container, `peer_ok` returns true) any host that can reach the port and sends `Host: 127.0.0.1:<port>` plus that header can POST /api/order. Measured: a python client with `X-Bagholder: 1` placed (dry) orders; without it, 403. docs/old-app-mistakes.md:63 records this as 'Not guarded yet'; docs/decisions.md (2026-09-25) says 'the page's write token stay[s]' though no token exists.
- evidence: rust/crates/server/src/http/mod.rs:301 (`!head("x-bagholder").is_empty()` is the whole write check); rust/crates/server/src/http/mod.rs:310 (peer_ok is unconditionally true when bound beyond 127.0.0.1); docs/old-app-mistakes.md:63 (acknowledged, unguarded); docker-compose.yml:12 (the default publishes on 127.0.0.1 only, which is what currently protects it)
- impact: A Pi or container whose port is published on the LAN (one line changed in compose) lets any device on the network place, modify and cancel real orders.
- proposal: Generate a random write token per install (kept in the data folder), have the page fetch it on load and send it on every POST, and require it whenever the bind is not loopback; keep the Host check. This is a page-and-server change with no new capability.
- ux-conflict: False

### robust-A-10 [medium/performance] The brackets ask Wealthsimple for a quote and a read-back every five seconds around the clock, sessions closed or not
- status: confirmed — code: confirmed | std: corrected (Confirmed by code: `bracket_loop` ticks every 5 s while any bracket is live (brackets.rs:408-419) and `quotes_for` calls `fetch_quotes` before `quoted()` sees `market_status != OPEN` (brackets.rs:361-366, 58-61); `ticket)
