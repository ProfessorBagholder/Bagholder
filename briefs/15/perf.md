## findings

### perf-A-1 [high/performance] Every quote pass re-reads the whole market cache once per priced instrument (O(holdings × closes), two SQLite opens each)
- status: confirmed — code: confirmed | std: confirmed
- standard: A change is applied from what changed: the reader has the instrument's quote in hand and the engine already takes a per-instrument Change::Quote (engine.rs:359-370). Established practice for tick handling (IB TWS API tickPrice, any broker screen) touches one instrument's state; the design's own §13 says a price updates only that instrument. SQLite's guidance and every pooled-connection design keep one connection per thread for a pass, not one per instrument (sqlite/src/pool.rs header states this itself).
- observed: due::pass calls f.price_changed(l.id) for every quoted listing and every held contract (due.rs:128-130, 136-138). price_changed opens a new Book connection and a new MarketCache connection (figures.rs:457-458 → figures.rs:206-218), and market() reads ALL quotes, ALL daily closes, ALL ex-dividends and ALL benchmark series of every instrument (read_sources.rs:45-62; cache.rs:246-282, 328-340, 432-470) to pick out one instrument's rows. Each open runs migrate::open twice on the file (read-only identify, then the real open: migrate.rs:125-131) with PRAGMA journal_mode, synchronous, user_version, application_id and a sqlite_master count. The same pattern is in benchmark_changed (figures.rs:467-471) and in read_all's per-close and per-payer loops (due.rs:219-233). Measured with the demo (20 listings + 9 contracts, 0 daily_closes rows, 2,166 benchmark_closes rows, offline): strace over 66 s with Portfolio open = 108 openat, 3,859 pread64, +15.4 MB rchar, 0.46 s CPU; one pass ≈ 0.1-0.2 s CPU (11-21 ticks jumps in the portfolio-idle samples).
- evidence: rust/crates/server/src/figures.rs:457 (price_changed: let m = market(&self.book()?, &self.cache()?)? — whole market read and two ); rust/crates/server/src/due.rs:128 (for l in &quoting { f.price_changed(l.id)?; } — once per quoted listing, every pass); rust/crates/server/src/due.rs:136 (for c in &needs.contracts { f.price_changed(c.id)?; } — and once per held contract); rust/crates/server/src/read_sources.rs:48 (market_from_cache: cache.quotes(), cache.closes(), cache.ex_dividends(), cache.benchmark_s); rust/crates/sources/src/cache.rs:328 (closes(): SELECT every standing close of every instrument on every day); rust/crates/server/src/figures.rs:206 (book(): Book::open_in on every call — a new connection with the migration check)
- impact: The cost of a minute's quote pass grows with holdings × stored history, not with what moved. A real book (say 40 holdings × ~700 daily closes = 28k rows, 6 benchmarks × 2,000 days = 12k rows) decodes ~1.2M rows and text-parses ~1.2M decimals per pass: roughly 1-2 s CPU per minute on this Xeon, 5-10 s per minute on a Pi 4 (10-15% of a core while any page shows holdings), 10-20 s on a Pi Zero 2, where the pass would not finish inside its own minute. It also holds the engine write lock (apply_if takes engine.write, figures.rs:314-320) once per instrument, so pages stall behind it.
- proposal: Give the cache per-instrument reads (quote_of(id), closes_of(id), ex_dividend_of(id)) and apply Change::Quote/Closes from them; open one Book and one MarketCache per pass (Ctx already holds both) and pass them into price_changed/payer_changed/rates_changed instead of reopening; batch a pass's applies under one engine write lock and one Moved. Add a test that counts connection opens and rows read per pass and fails when either grows with the number of holdings.
- ux-conflict: False 
- owner decision: -
- confidence: high

### perf-A-2 [high/narrow-fix] Showing a priced tab re-runs the whole read pass and re-quotes every holding with no freshness gate, although the owner's own rule for options forbids exactly this
- status: confirmed — code: corrected (The mechanism is exactly as described (docs.rs:189-195 wake on any PRICED key; due.rs:60-66 park ends; due.rs:126-127 read_quotes over everything demand returns; quotes.rs:111-176 asks every source unconditionally, read_) | std: confirmed
- standard: Sources are read because something changed or is needed, and a read that finds nothing new changes nothing (docs/architecture.md §13). Brokerage screens poll on a cadence with a cache TTL (Sharesight and Wealthsimple web refresh on a timer; a return within the interval shows the cached price). The owner's decision of 2026-09-24 states the same for option prices: 'fetched again only when a screen shows it, its market is open, and the stored one is older than the source can improve on ... A page opening or reloading never causes a fetch by itself', held by options::chain_due. A per-host limiter paces requests; it does not decide whether to ask.
- observed: Bus::watch calls docs::opened for every key the stream did not have (events.rs:187-199); for any PRICED key (positions, exposure, markets, heatmap, cashflow, trade) opened wakes the scheduler (docs.rs:189-195); the park ends on woken (due.rs:60-66) and pass() runs read_quotes for everything demand returns (due.rs:126-127) with no age check: read_quotes asks each listing's source unconditionally (quotes.rs:111-176; read_tmx only truncates forms after a NotCarried today, 197-203), while options::read is gated by chain_due (due.rs:134-138). The cache stores each quote's allowance_secs (cache.rs:228-239) and nothing reads it. Measured on the demo offline: ten positions-tab round trips cost 145 ticks (1.45 s) of server CPU, ~125 ms per wake-triggered pass beyond the signal cost; the page draws the tab from what it holds meanwhile.
- evidence: rust/crates/server/src/docs.rs:189 (opened(): a PRICED key wakes the scheduler at once); rust/crates/server/src/due.rs:62 (park_until_or(&app, wait, || f.woken()) — the wake ends the minute's wait); rust/crates/server/src/due.rs:126 (quotes::read_quotes(&ctx, &quoting) — every listing demand returns, whatever its stored qu); rust/crates/sources/src/quotes.rs:111 (read_quotes: no comparison with the stored quote's age or allowance); rust/crates/sources/src/cache.rs:239 (allowance_secs is written with every quote and read by nothing); rust/crates/server/src/due.rs:134 (the option contracts' chains are gated by chain_due — the gate listings lack)
- impact: Online, each visit to Portfolio, Markets, Cashflow or a trade page sends one HTTP request per holding to TMX/Yahoo/Coinbase (20-40 requests) and then again a minute later; flipping between Trades and Portfolio a few times triggers a hundred quote requests within a minute against sources with no contract and known rate limits, plus ~125 ms of server CPU per switch here (≈0.5-1 s on a Pi 4) for the whole-market re-read of A-1. Nothing on screen needed a fresh quote: the page draws the kept one at once.
- proposal: In demand()/read_quotes, quote only listings whose newest stored quote is older than QUOTES_EVERY (or the allowance the source stated, which is already stored) — the same rule chain_due applies to options — so the wake on opened costs nothing when quotes are fresh and the minute cadence is kept by next_due; keep the wake for a listing never quoted. Add a test: opening a priced tab twice within a minute makes one set of requests.
- ux-conflict: False 
- owner decision: docs/decisions.md 2026-09-24: 'Option prices on screen stay Cboe's delayed chains, fetched only when needed ... A page opening or reloading never causes a fetch by itself' — decided for options and held by chain_due; listings' quotes have no such gate.
- confidence: high

### perf-A-3 [high/design] Every signal wakes every parked loop, and their readiness predicates open database connections and read files (16-23 ms CPU per signal, ~9 file opens)
- status: confirmed — code: confirmed | std: confirmed
- standard: A condition-variable wait re-evaluates a cheap predicate (Rust std docs on Condvar; Hoare/Mesa monitors). Event-driven servers wake the waiter whose event it was (per-topic channels/watch receivers, which the code already has for streams: tokio::sync::watch). The design's own §13 rule: work is done because something changed, only that work.
- observed: Bus::signal_from is one bell for the whole process (events.rs:104-110): every commit on any connection, every write to app.state (app.rs:93-99), every watch POST and every stream open rings it. Six loops park on it with predicates that do I/O on every wake: bracket_loop → bracket_work opens a new Book connection and queries live brackets and in-flight orders (brackets.rs:400-405); watch_loop → csv_import::watching opens a new Book connection (csv_import.rs:447-449); broker_reads → Seen::changed → signed_in reads session.json from disk (broker_reads.rs:186-201, ws/session.rs:182-189); news_loop → news_wanted → notices → notify::book (a pooled or new Book) plus a settings query (feeds.rs:507-509, 174-178); filings_sweep_loop's wanted does the same with two queries (feeds.rs:1484-1488). Measured with one stream on `book` alone: 100 identical watch POSTs → 1.61 s CPU (16 ms each, strace attached); with `status` alone 2.35 s (23.5 ms); strace over the 200 signals: 1,746 openat, 17,136 newfstatat, 11,942 pread64, 11,350 fcntl — about nine file opens and eighty-five stats per signal. The status document adds its own rebuild per step (status.rs:64-99: opens the notices book, reads session.json again, reads the update record from the cache pool, GROUP BY over outcomes without an index (cache.rs:548-555), counts open orders) although docs are otherwise re-read only when their source's stamp moved (events.rs:427-431).
- evidence: rust/crates/server/src/events.rs:104 (signal_from: one bell, notify_all + ticker for every change from any source); rust/crates/server/src/orders/brackets.rs:400 (bracket_work: let Ok(book) = f.book() … live_brackets, orders_in_flight — on every wake); rust/crates/server/src/csv_import.rs:447 (watching(): f.book().ok()… setting(WATCH_FOLDER) — a new connection per wake); rust/crates/server/src/broker_reads.rs:199 (signed_in: session_file(app).load() — disk read per wake); rust/crates/server/src/feeds.rs:507 (news_wanted: notices(app) … notice_settings — a book connection per wake); rust/crates/server/src/events.rs:405 (status rebuilt on every step of every stream, not by a source stamp)
- impact: A quote pass online produces 2 commits per holding (perf-A-6) and a signal each (gathered per 40 ms for streams, but the loops wake per signal); with brackets live the 5-second readback commits too. Every open page multiplies the status rebuild. On this box a busy minute costs on the order of 0.5-1 s CPU of pure wake-ups; a Pi 4 spends 3-5 s of a minute waking loops that have nothing to do, and every wake is a fresh SQLite open (identify + migrate check) on an SD card.
- proposal: Split the bell by topic (the Source enum already exists: extend it, or give each loop a watch receiver on the counters it reads) so a commit to the market cache does not wake the bracket loop or the CSV watcher; make predicates read in-memory state (a live-bracket count kept in OrdersState, the watched folder in a Watched setting, the session presence in a flag set by the session loop); give status the same stamp rule as the other documents and cache its file-backed parts behind change counters; add an index on outcomes(source, host, kind, instrument_id, id). Hold it with a test that counts file opens per signal (strace-free: count Book::open calls) and fails above zero for a signal nobody's predicate depends on.
- ux-conflict: False

### perf-V-2 [high/narrow-fix] The page's chart read-ahead is served as if the person opened every chart: unpaced, four-way parallel, and allowed to ask Yahoo, the source the code reserves for an opened chart
- status: added by verifier
- standard: A speculative prefetch is served at lower priority and cost than a user action (browsers' own prefetch/prerender hints are deprioritised and cancellable; HTTP `Priority`/`Sec-Purpose: prefetch` exists so a server can tell); a rate-limited third-party source is asked only for what a person is looking at, which is the rule the code itself states for Yahoo (history.rs:688-690).
- observed: The page marks read-ahead only on its own side: chartAsDrawn passes `ahead = true` to loadHistory (web/src/lib/trade/ahead.ts:21-31) and read() uses it just to wait for idle (web/src/lib/trade/chart.ts:96-98; reads.svelte.ts:115); the /api/history query carries no such flag. On the server, history_payload (rust/crates/server/src/feeds.rs:3195-3250) treats every request alike: for an intraday timeframe not yet stored it calls ensure_intraday_in_background, which calls ensure_intraday with on_demand = true (rust/crates/market/src/history.rs:1005), and ensure_bars does the same (history.rs:1333). With on_demand true, fetch_intraday skips the ON_DEMAND_ONLY_SOURCES exclusion (history.rs:1115), so Yahoo is asked; fetch_tmx_minutes skips `pace_host("app-money.tmx.com", ARCHIVE_TMX_GAP)` (history.rs:852-854) and fetches its month chunks 4-way parallel (history.rs:859) instead of one at a time as the archive sweep does (history.rs:1240 passes false). The read-ahead runs over every trade and holding on every page load whose browser store is empty, and again for every chart that came back without bars (perf-A-4): measured 31 history requests on a first open and 14 on a second, each of which, online, is an on-demand fetch. So the rule 'asked for a chart someone opens, never by the background sweep' holds for the sweep and is defeated by the page.
- evidence: rust/crates/market/src/history.rs:690 (ON_DEMAND_ONLY_SOURCES = ["yahoo"]: 'asked for a chart someone opens, never by the backgro); rust/crates/market/src/history.rs:1005 (ensure_intraday_in_background → ensure_intraday(…, true): every page request is on demand); rust/crates/market/src/history.rs:1115 ((!on_demand && ON_DEMAND_ONLY_SOURCES.contains(…)) — Yahoo excluded only when on_demand is); rust/crates/market/src/history.rs:852 (if !on_demand { pace_host("app-money.tmx.com", ARCHIVE_TMX_GAP) } — the read-ahead is not ); rust/crates/market/src/history.rs:859 (parallel(chunks, if on_demand { 4 } else { 1 }, one) — four month chunks in flight per rea); rust/crates/server/src/feeds.rs:3218 (history_payload: ensure_intraday_in_background for any request whose bars are not stored; )
- impact: Online, a fresh open of a journal with a few hundred trades fires hundreds of history requests that each bypass the TMX pacing and run four fetches in parallel, and the ones that need Yahoo hit the one source the code knows is rate-limited — for charts nobody has opened. On a Pi behind a home connection this is the burst most likely to get the app's IP throttled by TMX or Yahoo, and when it does, the person's own opened chart is the one that fails, since it shares the limiter.
- proposal: Send `ahead=1` on read-ahead history requests and have history_payload map it to on_demand = false (paced, sequential, no ON_DEMAND_ONLY source) or answer read-ahead from stored bars only and leave the fetch to the archive sweep; keep on_demand = true for a chart on screen. Add a test that a request marked ahead never reaches an ON_DEMAND_ONLY source and never runs the parallel path. This stands whether or not the read-ahead scope of perf-A-4 is narrowed.
