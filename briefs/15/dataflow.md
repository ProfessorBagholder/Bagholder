## findings

### dataflow-A-1 [high/performance] One global bell: every change wakes every stream, which rebuilds the header and re-reads every store document whether or not it moved
- status: confirmed — code: confirmed | std: confirmed
- standard: Change propagation in live systems is keyed: a change invalidates the subscriptions that depend on it and nothing else (Firestore listen targets, GraphQL subscriptions per field, Replicache/RxDB per collection; the reactive-graph pattern of Svelte runes and Salsa). Work is computed once per change and fanned out, not once per client. The team's own §13: "only the work a change requires".
- observed: Bus::signal_from increments one counter and notifies everything (events.rs:110-116). Each stream's Feed::step then runs on the blocking pool for every signal: it rebuilds the whole header Status (events.rs:412-424 -> status.rs:63-130: opens a book connection via notify::book, reads session.json, the update meta row, the notices, orders_in_flight and live_brackets twice (status.rs:79 and events.rs:362), the market cache's newest-outcome query, feed and order failures), then re-reads every non-figure document whose kind lists Source::State (docs.rs:139-148: shorts, news, fear, universe, filings, filings-feed, history are all [Store, State]) because sources are per kind, not per document (events.rs:430-447). Source::State is signalled by any page's watch/scroll (events.rs:200), a stream opening or closing (events.rs:251, 258), the ticket quote loop every 5 s (docs.rs:47), a news pass per listing (feeds.rs:479-484), and the quote pass. Two browser tabs mean two independent rebuilds and two copies of every view's state (Trades.rows holds every in-scope trade per stream, views.rs:663-666).
- evidence: rust/crates/server/src/events.rs:110 (signal_from: one bell, notify_all, no key); rust/crates/server/src/events.rs:402 (step iterates every wanted document per signal); rust/crates/server/src/events.rs:430 (a doc is re-read when any commit of its Source kind happened, not when it moved); rust/crates/server/src/docs.rs:146 (default sources for every doc: [Store, State]); rust/crates/server/src/status.rs:63 (status(): book open, session file, update meta, notices, orders, source failures per call); rust/crates/server/src/http/stream.rs:119 (every step runs feed.step on the blocking pool per stream)
- impact: Measured 14.8 ms of server CPU per signal with one page on the Markets tab (11 documents) while nothing changed and nothing was sent; a ticket open adds a signal every 5 s, each open tab multiplies it. On a Raspberry Pi (roughly 8-10x slower) that is ~100-150 ms of CPU per signal per tab, spent on reads and diffs that produce no message, competing with the bracket engine and the pull on the same blocking pool.
- proposal: Key the bus: a signal names what changed (a document key, an entity kind, a table) and a stream steps only the subscriptions that depend on it; split the header into small documents (connection, sync, update, failures, counts) each recomputed by its own trigger; compute a document's new state once per change and fan the same patch out to every stream that shows it; hold the per-source read stamps per document, not per kind.
- ux-conflict: False 
- owner decision: -
- confidence: high

### dataflow-A-2 [medium/design] Resume by version is the recorded design, but the reconnect path defeats it: the browser replays the first connect's 'have' and Bus::watch discards a fresher one
- status: confirmed — code: confirmed | std: corrected (Half of the finding judges a recorded design choice as a broken promise. docs/plans/stage-5 line 127 records the departure with its reason: resume per subscription by version, not by replaying numbered changes, because a)
- standard: A client resumes from a cursor it holds now: Replicache's pull cookie and Firestore's resume token are the versions the client holds at reconnect, not at first connect; WHATWG server-sent events reconnect automatically to the original URL, so a page that encodes state in the URL must reopen the EventSource itself with its current state.
- observed: The stage-5 plan chose resume per subscription by version and says why (docs/plans/stage-5, line 127); Feed::first answers 'same' when the page's have equals the current version (events.rs:378-385). But the EventSource URL carries the docs and have of the first connect (live.svelte.ts:400) and es.onerror only sets flags (live.svelte.ts:484-488), so the browser's automatic reconnect states the first connect's screens and versions; then Bus::watch keeps the old Want for any key whose params are unchanged and drops the fresh have the page posts (events.rs:190-193). Figures::moved_since keeps 256 changes (figures.rs:272-290, 481) but a new Feed starts at 0 and never uses it. SSE ids restart at 1 per connection (stream.rs:136) and the resync-on-gap path guards a gap an ordered TCP stream cannot produce.
- evidence: docs/plans/stage-5-dataflow.md:127 (the recorded departure: resume per subscription by version, with its reason); web/src/lib/live.svelte.ts:400 (EventSource URL fixes docs and have at first connect; the browser replays it); web/src/lib/live.svelte.ts:484 (onerror does not reopen with shownNow()); rust/crates/server/src/events.rs:190 (watch keeps was.clone() for same params: the page's fresh have is dropped); rust/crates/server/src/http/stream.rs:136 (ids enumerate from 1 per connection; Last-Event-ID unused on /api/events)
- impact: Every drop resends whole documents that moved since the page was first opened, including screens no longer on show (B-2 measured 42 KB on the demo after one restart); the design's own resume exists but never runs on a reconnect.
- proposal: Keep the version-per-subscription design and make it hold: on error, close and reopen the EventSource from the page with shownNow() (current docs and current have); let Bus::watch take a fresher have for an existing key; drop the per-connection numbering and the resync-on-gap path, or turn the number into a real cursor.
- ux-conflict: False 
- owner decision: -
- confidence: high

### dataflow-A-3 [high/performance] A first open reads the whole book into the browser: every trade's fills and every trade's chart, and the fills and every trade again on every page load
- status: merged — code: refuted (Same root cause as B-3 (every page load reads every trade, every trade's fills and every trade's chart ahead), which is kept because it also names the server-side consequence (a page GET starting a source fetch, feeds.rs) | std: corrected (The facts hold and I re-measured them on the 31-trade, 11-holding demo: first open made 57 API responses, 376 KB (42 GET /api/history for 327 KB, details 28.4 KB, every trade 20.7 KB, 13 POST /api/events/watch of priming)
- standard: Journals and brokerage screens load a trade's chart and executions when the trade is opened (Tradervue, TradeZella, IBKR's trade log), page long lists, prefetch on intent with a bounded budget, and never re-fetch a large unchanged payload on every load; the team's own §13 (docs/architecture.md:189): opening the page makes the server do nothing new.
- observed: On the demo (31 trades, 11 holdings) the first open made 57 API responses, 376 KB: /api/figures/trades (20.7 KB, every trade, App.svelte:218), /api/figures/details (28.4 KB, every trade's and holding's fills, ahead.ts:43), 42 GET /api/history read one after another by readAhead (ahead.ts:45-52), and 13 POST /api/events/watch (each primed document dropped triggers another watch, live.svelte.ts:218-225). primeScreens subscribes every tab, the heatmap, every universe, the news, shorts, both fear meters and the orders at once (App.svelte:173-189; live.svelte.ts:228-242). After that one open the browser held 87 entries, 690 KB (39 drawn charts 320 KB, 32 'get:' answers 275 KB). A reload skipped the read-ahead (charts recalled) but fetched /api/figures/trades and /api/figures/details again in full (reads.svelte.ts:45 ASKED_EACH_TIME; ahead.ts:43), rebuilt by the server before the 304 is decided (A-4).
- evidence: web/src/lib/trade/ahead.ts:43 (every page load reads /api/figures/details, then a chart per trade and holding); web/src/App.svelte:173 (everyScreen: 14 subscriptions primed on first open); web/src/App.svelte:218 (every trade read each page load); web/src/lib/live.svelte.ts:228 (primeScreens subscribes every screen not yet kept); web/src/lib/reads.svelte.ts:45 (ASKED_EACH_TIME: figures/trades read on every page load)
- impact: Cost grows linearly with the book: a 2,000-trade journal means thousands of paced chart reads per fresh browser profile (each device, each Clear all, each PROTOCOL bump) and a multi-megabyte details payload rebuilt on every page load; on a Pi the first open of a real book takes minutes and the load-time payload dominates memory.
- proposal: Keep the owner's rule (never an empty screen) by keeping what was shown, not by pre-reading everything: page /api/figures/details by trade id (the open trade's fills only), read a chart on the first open of its page and keep it, prime only the tabs' documents; where read-ahead stays, bound it (the newest N trades, idle-time only, one per idle tick) and never re-fetch a payload whose version the page already holds.
- ux-conflict: True — A trade page never opened before would draw its executions at once but its chart on arrival instead of pre-drawn; the owner's 2026-09-28 decision names tabs and screens, and the team extended it to every trade's chart (brief 14).
- owner decision: 2026-09-28 (no screen ever opens with nothing; every tab kept from the first open) and brief 14 ('charts are read ahead', accepted)
- confidence: high

### dataflow-A-4 [medium/design] Conditional reads validate after the work is done, and one read is cached three times on the page
- status: confirmed — code: confirmed | std: confirmed
- standard: RFC 9110 §13.1.2: a validator lets the origin skip generating the representation; the cheap validator is a stored version (an updated-at or row version), and immutable data carries Cache-Control: immutable (RFC 8246). One cache layer per client is the pattern of SWR/TanStack Query/Apollo.
- observed: The ETag is FNV-1a over the finished body, computed after the route ran and the whole body was buffered (http/mod.rs:245-270, up to BODY_LIMIT*4 = 128 MB); a 304 saves bytes only. Measured: /api/figures/details 200 in 3.4 ms, 304 in 3.2 ms; /api/history 1.4 vs 1.3 ms. Every GET is 'private, no-cache'; the plan's 'a closed session's bars carry immutable' is not built (history answers no-cache). On the page a read is held in the browser's HTTP cache (revalidated by ETag), in the 'asked' map (reads.svelte.ts:56) and in IndexedDB (reads.svelte.ts:125), and the IndexedDB copy is structuredClone'd and rewritten on every answer including an unchanged 304.
- evidence: rust/crates/server/src/http/mod.rs:256 (tag computed from the bytes of the finished answer); rust/crates/server/src/http/mod.rs:259 (every GET answer: private, no-cache; no immutable for closed bars); web/src/lib/reads.svelte.ts:125 (save to IndexedDB on every answer, changed or not); web/src/lib/reads.svelte.ts:56 (a second in-memory cache beside the browser's HTTP cache)
- impact: The server does the full read and build for every revalidation (every page load's details and trades, every chart open), so on a small board the 'unchanged' answer costs the same as the change; the page pays three copies and an IndexedDB write per read.
- proposal: Derive the validator before the work: a version the store keeps (the book's sequence for figures routes, the bar archive's last close for history) compared with If-None-Match before building; mark a closed session's bars and a filed document immutable; keep one cache on the page (the kept store) and let the browser's HTTP cache go for API reads, writing to IndexedDB only when the version changed.
- ux-conflict: False 
- owner decision: -
- confidence: high

### dataflow-A-5 [medium/performance] The browser-kept copy is whole documents per parameter set, unbounded, read whole at every open and rewritten whole on every patch
- status: confirmed — code: confirmed | std: confirmed
- standard: Client stores that make an open instant are normalized by entity id, bounded with eviction and indexed by key (Replicache, RxDB, Apollo cache; briefs/reference.md 'Normalized stores'); a patch writes the rows it touched.
- observed: kept.ts files each document under key+JSON(params) (kept.ts:66), so every filter, sort and limit combination keeps a full separate copy of the trades or cashflow document. keepChanged deep-copies ($state.snapshot) and puts the whole document on every patch (live.svelte.ts:511-518; a quote tick rewrites positions 38 KB, dashboard 38 KB, heatmap, markets). readKept loads every entry for the book into memory at every open (kept.ts:79-107); keptLatest scans every key linearly (kept.ts:130) and is called per watchDoc and per keptRow. After one walk of the 82-trade demo the store held 289 entries, 1.14 MB of JSON (134 drawn charts 342 KB, 137 'get:' answers 611 KB, including a 213 KB details copy and a 51 KB second copy of every trade). Nothing evicts.
- evidence: web/src/lib/kept.ts:66 (one full copy per key and params); web/src/lib/live.svelte.ts:511 (whole-document snapshot and put per changed document per message); web/src/lib/kept.ts:90 (the whole store read into memory at every open); web/src/lib/kept.ts:130 (keptLatest: linear scan over every entry)
- impact: Memory and open time grow with trades x timeframes x filter combinations; a real book with years of charts and a person who filters often will carry many megabytes into memory on every open and rewrite tens of kilobytes per price tick, on a phone or a laptop browser too.
- proposal: Store rows by entity id with the document as an ordered list of ids; write the touched rows per patch; index by key (a key path or a second object store) so 'latest of key' is a lookup; bound the store (by bytes, LRU on last shown) and evict charts of closed trades first; keep one copy of a list across parameter sets.
- ux-conflict: False 
- owner decision: -
- confidence: high

### dataflow-A-6 [medium/performance] Most screens are rebuilt whole and re-hashed on every relevant change; the engine's per-entity report is thrown away at the view layer
- status: confirmed — code: confirmed | std: confirmed
- standard: Incremental view maintenance: a change updates the rows it touches and the aggregates over them (the team's own views.rs header and §13). Versioning is by sequence, not by hashing the whole state per message.
- observed: Whole<T>, Followers<T>, Headlines and CashflowView rebuild their entire document and diff it on any entity move they read (views.rs:263-271, 316-324, 407-415, 807-815). Headlines rebuilds for any Position move, which a single holding's quote is (views.rs:396 'Entity::Position(..) => true'): every minute per priced page, every story is re-filtered and re-sorted. CashflowView rebuilds on any Position move too (views.rs:799). Every patch computes v = hash of the whole document serialized (views.rs:191-193 via version() at 273, 325, 416, 539, 816); Trades::version() clones and serializes the window each time (views.rs:748-750).
- evidence: rust/crates/server/src/views.rs:396 (Headlines reads every Position move (a quote)); rust/crates/server/src/views.rs:799 (Cashflow rebuilt whole on any Position move); rust/crates/server/src/views.rs:191 (version_of: serialize the whole document to hash it, per message); rust/crates/server/src/views.rs:748 (Trades::version clones the window and serializes it)
- impact: Per quote tick per stream the server does O(document) work for the News, Cashflow, exposure, markets and heatmap documents to send a few fields; on a Pi with a thousand stored headlines and a few dozen holdings that is real CPU every minute while the Markets tab is open.
- proposal: Give each view a dependency set at row level (which instrument ids and which fields), so a quote updates the tags of the stories that name that listing and the one tile; take the version from the figures' sequence at the time of the change rather than hashing; keep whole-rebuild only for true aggregates (the dashboard statistics).
- ux-conflict: False 
- owner decision: -
- confidence: high

### dataflow-A-7 [medium/ui-ux] A filter or sort change shows the previous state under other parameters as if it were the new one, with no sign it is being revalidated
- status: confirmed — code: confirmed | std: confirmed
- standard: Stale-while-revalidate UIs keep the old content but mark it as revalidating (SWR isValidating, TanStack Query isFetching; TradeZella and Tradervue dim or spin the list on a filter change; IBKR marks frozen versus live data). A figure shown under a filter it does not match is, in a trading journal, a wrong figure.
- observed: watchDoc draws kept(book, key, params) ?? keptLatest(book, key) (live.svelte.ts:335): with a new filter the list, its totals and the dashboard's statistics are the last state under whatever parameters, drawn beside chips that say otherwise, until the server's snapshot arrives; the page shows no revalidation state (decisions.md 2026-09-28 forbids a placeholder where a value exists, but says nothing against a revalidating mark). Over loopback the window is milliseconds; over a tunnel to a Pi it is hundreds of milliseconds, and after a lost connection indefinite.
- evidence: web/src/lib/live.svelte.ts:335 (a screen under new params draws the last kept under any params); web/src/lib/kept.ts:126 (keptLatest: 'the last thing kept under any parameters'); web/src/lib/subs.svelte.ts:39 (applyFilters: a new subscription, the old rows shown meanwhile)
- impact: A person applying 'TFSA' or 'this year' can read the previous scope's P&L and win rate under the new chips; nothing on screen says the figures are not yet the ones asked for.
- proposal: Keep the last rows on screen but mark the screen as revalidating (a subtle state on the filter bar or the card header, never a placeholder), and do not present totals under parameters they were not computed for; clear the mark on the snapshot or 'same'.
- ux-conflict: True — Today the previous state is shown unmarked; the proposal adds a revalidating state, which the owner may read as a loading state.
- owner decision: 2026-09-28: a screen whose parameters changed shows the last it had until the new one arrives; no placeholder or loading state where a previous value exists
- confidence: high

### dataflow-A-8 [medium/robustness] Failures inside the stream are swallowed: a document that panics or cannot be read simply stops arriving, and an unknown key is ignored
- status: confirmed — code: confirmed | std: confirmed
- standard: Architecture §15 and decisions 2026-09-22 (a failure is always visible); live protocols answer a failed subscription with an error on that subscription (GraphQL-ws 'error' per id, Firestore listen with a status per target).
- observed: Feed::step wraps docs::read in catch_unwind and on a panic or a None does 'continue' (events.rs:437): the page keeps whatever it held, no 'refused', for ever. docs::read turns a store failure into None ('notify::book(app).ok()?', list_notifications '.ok()?', docs.rs:164-167), so the bell silently stops updating. A key neither views::open nor docs::read knows is dropped without a word (views.rs:97-99 returns None; events.rs:437). status_for parses the page's filters with unwrap_or_default (events.rs:348): an unreadable filter silently counts every account's orders in the badge.
- evidence: rust/crates/server/src/events.rs:437 (catch_unwind ... else { continue }: a panicking document is skipped silently); rust/crates/server/src/docs.rs:164 (store failures become 'no document'); rust/crates/server/src/events.rs:348 (filters that do not parse fall back to none)
- impact: A screen can sit on stale figures indefinitely with the header green; the owner's rule that nothing is caught and discarded is broken exactly where the page's data comes from.
- proposal: Answer every subscription: a read that fails or panics sends 'refused' with the reason on that key and is retried on the next change; an unknown key is refused; a filter that does not parse refuses the status subscription rather than defaulting.
- ux-conflict: False 
- owner decision: -
