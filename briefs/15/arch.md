## findings

### arch-A-1 [high/design] Execution and broker capabilities live in the server against Wealthsimple's own types, not behind the broker adapter
- status: merged — code: refuted (Same root cause as arch-B-2 (broker specifics decided outside the adapter, execution on the old ws transport in the server), which is kept: B-2 covers everything A-1 cites and more (statement codes in the broker crate, b) | std: confirmed
- standard: A broker adapter owns everything the broker does: reads, order placement, read-back and a declared capability set the rest of the app consults (ccxt's per-exchange `has` map; QuantConnect Lean's `IBrokerageModel.CanSubmitOrder`/order-type support per security; the repository's own docs/architecture.md §10: 'Capabilities, declared... Execution: place, modify, cancel, read one order back... A second brokerage is a new adapter; the book, the engine, execution and the page do not change for it').
- observed: `BrokerAdapter` (broker/src/lib.rs:197-285) has only reads and statements: no place/cancel/modify/read-back and no capabilities. Order execution is a second trait defined in the server (`OrderBroker`, orders/gate.rs:48-54) whose only implementation calls Wealthsimple's GraphQL mutations through the old `bagholder_ws` crate (gate.rs:225-244, 313). Broker facts are decided by name in the server: what is tradable (`info.broker == Broker::named("wealthsimple") && ...`, wire/build.rs:391), the coin dust minimum (engine_inputs.rs:19-21), whether a stop order is allowed (ticket.rs:341-352, from Wealthsimple's `allowed_order_subtypes`), listing lookup returning the old model's `Security` (ticket.rs:99-107, 402). Only one connection is ever created or pulled (pull_broker.rs:63-66, broker_reads.rs:95-98). Orders and brackets are keyed by broker string ids, symbol and currency, with no InstrumentId or AccountId (book/src/orders.rs:22-40; schema v22 `orders`, `brackets`).
- evidence: rust/crates/broker/src/lib.rs:197 (BrokerAdapter trait: accounts/activity/units/cash/history/statements only; nothing about o); rust/crates/server/src/orders/gate.rs:48 (OrderBroker trait declared in the server; impl at 229 uses bagholder_ws wire types (232-24); rust/crates/server/src/wire/build.rs:391 (tradable decided by comparing the broker name to "wealthsimple"); rust/crates/server/src/engine_inputs.rs:19 (coin_minimum returned only when broker == wealthsimple; a broker fact chosen by name in th); rust/crates/server/src/orders/ticket.rs:341 (stop_allowed read from Wealthsimple's market-data reply and cached per security id in App); rust/crates/server/src/broker_reads.rs:95 (the one Wealthsimple connection is created by name; no loop over book.connections())
- impact: A second brokerage (the stated direction, architecture §2) touches the 4,119-line orders module, the wire builder, the engine-input loader and both broker loops, and cannot be tested through the fake-broker harness the gate has today. Every order rule (stop support, time in force, coin minimum, which accounts can trade) is a condition scattered through the server rather than a capability the adapter states.
- proposal: Move execution into the broker contract: `bagholder_broker::execution` with place/cancel/modify/read-back and a `Capabilities` value (order kinds per instrument kind, stop support, TIF and GTC limit, coin minimum, whether duplicate client ids are refused, statement issuance); the Wealthsimple implementation lives in `crates/wealthsimple` on its own session client; `tradable`, `stop_allowed` and `coin_minimum` read the capabilities; orders and brackets carry AccountId/InstrumentId beside the broker's ids; pulls iterate the book's connections.
- ux-conflict: False 
- owner decision: docs/decisions.md 2026-09-23 'A second brokerage is expected... nothing is built for a second one until asked' and 2026-09-26 'the rewrite is a migration'; docs/plans/stage-4-execution.md put 'any second broker' out of scope.
- confidence: high

### arch-A-2 [high/design] Two identity models: figures key on InstrumentId, but news, filings, short interest, exposures, universes and chart bars still key on bare symbol strings and Wealthsimple security ids through the retired model/store crates
- status: merged — code: refuted (Same root cause as arch-B-1 (the unfinished cutover: a second, symbol-keyed identity in the earlier readers' tables and the four retired crates still compiled), which is kept because its evidence is broader and exactly m) | std: confirmed
- standard: One instrument identity for every feature (Interactive Brokers' conid, Sharesight's instrument id, OpenFIGI): a ticker change, a venue move or a dual listing never splits or merges market context. The repository's own architecture §5: 'Routing a request to the right source form is a lookup in those references... never code that knows tickers'; §17: 'only adapters depend on a source's reply types'.
- observed: The server rebuilds the old model's `MarketBase` by rendering the engine's positions and trades back into symbol/exchange/currency strings (market_context.rs:142-199) and re-creates `bagholder_model::securities::Security` rows keyed by Wealthsimple's security id, skipping any instrument without one (market_context.rs:204-231, `let Some(id) = ws_id(i.id)? else { continue }` at 214). The cache tables the readers write are keyed by symbol: news (id, symbol, exchange), filings (symbol, id), shorts (symbol, exchange), price_bars (symbol, tf, ts) (sources/migrations/004-the-earlier-readers.sql:22, 46, 95, 138). feeds.rs functions take (symbol, exchange, currency) throughout (feeds.rs:553, 643-655, 1622, 2262); wire/context.rs:19-24 converts the old store's floats back to decimals at a 'door'. SPEC.md:246 admits bars are 'stored under the bare ticker, so a company listed on both markets has one set of them'. The four old crates remain compiled and used (model 8,862 lines, store 7,126, ws 1,808, market 11,956; 33 server files reference them).
- evidence: rust/crates/server/src/market_context.rs:214 (securities(): an instrument with no Wealthsimple security id is silently left out of the m); rust/crates/server/src/market_context.rs:142 (build(): engine figures rendered to strings and poured into bagholder_model::context::Mark); rust/crates/sources/migrations/004-the-earlier-readers.sql:138 (price_bars PRIMARY KEY (symbol, tf, ts); news (22), filings (46), shorts (95) likewise sym); rust/crates/server/src/feeds.rs:2262 (read_shorts(symbol, exchange, currency, ...): the market readers' whole API is string-keye); rust/crates/server/src/wire/context.rs:19 (dec_of(f64): the earlier store's floats crossing back into the decimal figure path); SPEC.md:246 (the spec itself records the dual-listing defect caused by symbol-keyed bars)
- impact: A CSV-only or second-broker instrument (no Wealthsimple id) gets no news, filings, short interest, sector or chart context at all; a ticker change or a dual listing keys context under the wrong or a shared symbol; two persistence and two type vocabularies must be kept in step for every new screen; ~30k lines of retired code stay in the build and the binary.
- proposal: Give the context tables an `instrument_id` column (and kind) in the market cache, resolve source forms through `instrument_routes`, make the readers take `InstrumentId` + the listing's names, delete `MarketBase`/`securities()` and the model/store/ws crates once the session client moves into the Wealthsimple adapter. Do it table by table (shorts and bars first, where the dual-listing bug is user-visible).
- ux-conflict: False 
- owner decision: docs/decisions.md 2026-09-26 'The rewrite is a migration: nothing new is built in it'; docs/plans/stage-6-cutover.md line 15 keeps bagholder_market's readers and bagholder_ws as they are.
- confidence: high

### arch-A-3 [high/ui-ux] The journal is a thesis, one letter grade and untyped tags: no setups, mistakes, plan/risk or R-multiple, no per-execution notes, and no breakdown by tag beyond filtering
- status: confirmed — code: confirmed | std: corrected (The standard and the gap hold (TradeZella, TraderSync and Edgewonk model setups, mistakes and planned risk; Tradervue has notes and tags with reports by tag), but the observed overstates it: tags and grades are already f)
- standard: Every leading journal models the review as typed entities and reports on them: TradeZella (setups, mistakes, custom tag categories, playbooks, planned R, rating; reports by setup and mistake), TraderSync (setups, mistakes, custom tags, R-multiple; reports per setup), Edgewonk (setups, mistakes, emotions), Tradervue (notes per trade and per execution, tags; reports by tag). From each product's public feature and help pages; exact field names not verifiable offline.
- observed: JournalEntry is thesis, grade (A/B/C/F) and untyped tags (core/src/journal.rs:47-70), the grade scale is a schema CHECK (book/schema/v22.sql:249), and the wire carries exactly grade, thesis, tags (web/src/lib/generated/wire.ts:71, 96). Tags and grades are filter axes (scope.rs:84, 204-206), so every tile can be scoped to one tag; but the only journal-derived groupings are Grade buckets and the review queue (scope.rs:618-638), By symbol groups by underlying only (592-611), Kpi has no R, risk or planned-vs-actual field (303-328), and nothing attaches to an execution.
- evidence: rust/crates/core/src/journal.rs:66 (JournalEntry: thesis, grade, tags; nothing else the person can record); rust/crates/book/schema/v22.sql:249 (grade CHECK (grade IN ('A','B','C','F')): the scale is a schema constraint); rust/crates/engine/src/scope.rs:84 (Filters.tags: a tag is a filter axis already, so per-tag figures exist by filtering, not b); rust/crates/engine/src/scope.rs:303 (Kpi: no R-multiple, risk or planned-vs-actual); rust/crates/engine/src/scope.rs:592 (the only breakdown table built from trades is by underlying)
- impact: The product cannot answer which setup pays, which mistake costs or whether risk was respected without the person filtering one tag at a time; adding a category later is a schema change and a new filter axis on every screen.
- proposal: Model tags with a category (setup, mistake, emotion, custom) and a small per-trade plan (planned entry, stop, target, risk; R-multiple derived from the engine's exact figures); allow a note per execution; add a By-category breakdown built the way By symbol is, over the existing Filters. Keep A/B/C/F as one category among them, not a column constraint.
- ux-conflict: True — Adds fields to the trade page and a breakdown to the Dashboard; the standing rule is 'nothing on screen the owner did not ask for' (SPEC §1).
- owner decision: docs/decisions.md 'Only what was asked' (Earlier) and 'Make the app work properly as it is; nothing is built for expansion the owner hasn't asked for' (2026-09-24).
- confidence: high

### arch-A-4 [medium/robustness] The journal is the one thing in the book with no history: each save deletes the row and re-inserts, and an empty save erases the note for good
- status: confirmed — code: confirmed | std: confirmed
- standard: A trading journal's notes are the irreplaceable data; the repository's own book keeps every revision of every source record (record_revisions, architecture §6 'never lost... what the person wrote') and the design's own rule is 'nothing in it is ever lost' (book/src/lib.rs:1-5). Note-taking products keep version history (Notion, Obsidian sync, Google Docs); Tradervue and TradeZella keep notes editable but I cannot verify they version them.
- observed: `Book::set_journal` deletes the existing journal row and its tags, then inserts a new row (book/src/trades.rs:333-361; delete at 344-345); when the incoming entry is empty it returns after the delete (347), so a page that posts an empty form (or a stale client sending the three fields whole, which http/model.rs:173 says it always does) removes the thesis with no trace. `journal.id` changes on every save, so nothing can reference a note stably.
- evidence: rust/crates/book/src/trades.rs:344 (DELETE FROM journal_tags / DELETE FROM journal before every insert); rust/crates/book/src/trades.rs:347 (an empty entry returns after the delete: the previous note is gone); rust/crates/book/schema/v22.sql:246 (journal table has updated_at only; no revisions table); rust/crates/server/src/http/model.rs:173 (the page sends the whole entry on every save)
- impact: One mis-save (an emptied textarea, a race between two open pages, a bug in the page) destroys the only copy of what the person wrote about a trade; the book's 'never lost' promise is broken exactly where it matters most.
- proposal: Append-only `journal_revisions(subject, revision, at, thesis, grade, tags)` with the current entry a view of the latest; an empty save becomes a revision marked cleared, restorable; keep the journal row id stable.
- ux-conflict: False 
- owner decision: -
- confidence: high

### arch-A-5 [medium/design] One hard-wired lot method (FIFO per account) serves both trade P&L and the holding's Avg cost, so the app's Avg cost and Cost basis disagree with Wealthsimple's own screen after any partial sale
- status: confirmed — code: confirmed | std: confirmed
- standard: Journals let the lot method be chosen (TraderSync: FIFO, LIFO or weighted average) and portfolio trackers separate trade matching from position cost (Sharesight: FIFO/LIFO/highest/lowest/minimise-gain per market, average cost where the tax rule is average; IBKR: FIFO/LIFO/specific lot/average). For a Canadian in a non-registered account the CRA's adjusted cost base is average cost across all accounts of identical property, and Wealthsimple itself displays average cost.
- observed: Lots close from the front of a per-(account, instrument) deque (engine/src/ledger.rs:889-949) and the position's Avg is the remaining FIFO lots' value ÷ units (positions.rs:159-163); SPEC.md:20 fixes 'Lots are matched first-in first-out within that account and instrument' and the open-to-flat plan says 'the choice of method is not changed here' (docs/plans/trade-open-to-flat.md:21). No method enum exists anywhere in the engine.
- evidence: rust/crates/engine/src/ledger.rs:896 (close(): always the front lot; no method parameter); rust/crates/engine/src/positions.rs:159 (avg = remaining lots' book ÷ units: FIFO residue, not average cost); SPEC.md:20 (the definition fixes FIFO for trades and, by §2 Position, for the holding); docs/plans/trade-open-to-flat.md:21 (method choice explicitly not made)
- impact: Buy 100 @ 10, buy 100 @ 20, sell 100: Bagholder shows Avg cost 20.00 and Book 2,000 for the remaining 100; Wealthsimple shows 15.00 and 1,500. Portfolio's Cost basis, Unrealized P&L %, Yield on cost and the tax-relevant cost of every partly sold holding differ from the broker the app is built for, with no way to reconcile.
- proposal: Keep FIFO as the journal's realized-P&L method (the category norm) but make the method a typed engine input per purpose: trade matching (FIFO) and position cost (average cost, the broker's and CRA's) at minimum, with the enum ready for LIFO/specific lot. The lot deque and `share()` already support it; the cases would gain a method column.
- ux-conflict: True — Avg cost, Book and Cost basis on the Portfolio page would change for partly sold holdings to match Wealthsimple's figures.
- owner decision: SPEC.md §2 Trade (FIFO) and docs/decisions.md 2026-09-24 (trade runs open to flat; method unchanged).
- confidence: high
