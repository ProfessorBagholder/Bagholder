### storage-A-1 [high/robustness] A failed update after a schema migration leaves a book the rolled-back binary refuses to open, with only a log line
- status: confirmed — code: confirmed | std: corrected (The code path is exactly as described (update.rs:593-608 restores HOME/previous only; migrate.rs:164-166 refuses a newer file; main.rs:158-161 exits 1; docker-compose restart loops). Two corrections: the cited standard m)
- standard: An automated rollback is all-or-nothing: pg_upgrade keeps the old cluster untouched until the new one is verified, and a supervisor that puts an old binary back must put back the data that binary can open or say what to do. Firefox does not fall back: since v67 it refuses a profile written by a newer build and shows the person a dialog naming the way out; refusing is acceptable, refusing with a log line only is not. The app's own contract says the same (docs/architecture.md §16 line 220: 'returns to the previous version and snapshot') and the owner's rule 2026-09-22: 'a failure is always visible: never a log line only'.
- observed: The updater keeps only the previous executables (update.rs:471-486 keep_previous) and restore_previous/rollback_in (update.rs:575-608) put back files from HOME/previous; nothing in update.rs mentions a snapshot. The book's migration does take one (migrate.rs:178-179, book-v<N>-<stamp>.db in snapshots/), but nothing restores it. migrate::identify refuses a file whose user_version is above the build's (migrate.rs:164-166, MigrateError::Newer, which names schema numbers, not the snapshot), and main.rs:158-161 logs and returns 1. So release N+1 migrates 22 to 23, dies inside the healthy window, the supervisor restores binary N (update.rs:843), binary N refuses the book and exits 1; the update-failed marker (update.rs:850) is written for 'the server started next' to say in the header, but no server starts. In the container (docker-compose.yml:17, restart: unless-stopped) the same refusal repeats on every restart.
- evidence: rust/crates/server/src/update.rs:593 (rollback_in puts back files from HOME/previous only); rust/crates/server/src/update.rs:843 (supervisor: restore_previous then continue; the book is untouched); rust/crates/sqlite/src/migrate.rs:164 (identify: from > known -> Newer, the file is refused); rust/crates/sqlite/src/migrate.rs:178 (the snapshot is taken before migrating and never read again by the app); rust/crates/server/src/main.rs:158 (Figures::open Err -> log and return 1); docker-compose.yml:17 (restart: unless-stopped)
- impact: An in-app update that carries a schema change and fails to come up ends in no running app and no visible message naming the snapshot to copy back; a Docker user who pins an older image after a bad release meets a restart loop.
- proposal: Record the book's and cache's schema versions in the pending marker before the swap; on the supervisor's rollback inside the healthy window, restore the matching snapshots from snapshots/ before starting the old binary (the window bounds what is lost). Outside that window, when identify() finds a newer file, the server still starts and shows the refusal on the page with the snapshot's path, instead of exit 1. Cover both with the supervise stand-in test using a fake migration 23.
- ux-conflict: False 
- owner decision: docs/decisions.md 2026-09-26: 'The rewrite is a migration: nothing new is built in it' puts safer updates and the book's restore out of scope; docs/decisions.md 2026-09-22 'a failure is always visible: never a log line only' cuts the other way.
- confidence: high

### storage-A-2 [high/performance] Cash and buying-power statements are appended every five minutes, never pruned, and read by a full scan
- status: contested — code: refuted (Every observation is accurate (pull.rs:686-729 store_cash/store_buying_power per account per read with no comparison, broker_reads.rs:36 BALANCES_EVERY 5 min, statements.rs:213-222 one statements row plus a statement_cas) | std: confirmed
- standard: Brokerage and journal products keep balances as one current value plus a daily history: Interactive Brokers' Flex/Activity statements carry one NAV per day, Sharesight keeps daily valuations, Wealthsimple's own app shows daily net value (the source this app reads). An append-only log of intra-day readings is an audit trail, and audit trails have a retention rule and an index on the key they are read by (SQLite docs, 'CREATE INDEX' on columns used in WHERE and ORDER BY).
- observed: broker/src/pull.rs balances() calls book.store_cash for every account on every balances read, and store_buying_power for every margin account; each call inserts a statements row plus one statement_cash row per currency, and each read inserts a broker_reads row, with no comparison against the last statement (unlike store_account_days, which writes only a changed day). broker_reads.rs reads balances every BALANCES_EVERY = 5 minutes while a page is open and at every page open. Nothing deletes or rolls up these rows. Book::stated() then runs 'SELECT id, stated_at FROM statements WHERE account_id = ? AND kind = 'cash'' with no index on statements beyond its id primary key, parses every stated_at into a Timestamp, sorts the whole vector, and keeps two entries; stated() is called for every account on every engine build (engine_inputs.rs:100). With the owner's 29 accounts (docs/plans/stage-6-cutover.md line 123) and two currencies that is about 88 rows per read, ~1,050 rows per hour a page is open, on the order of 2-3 million rows a year, all scanned per account per rebuild.
- evidence: rust/crates/broker/src/pull.rs:700 (store_cash on every balances read for every account, no change check); rust/crates/broker/src/pull.rs:726 (store_buying_power on every read for every margin account); rust/crates/server/src/broker_reads.rs:36 (BALANCES_EVERY = 5 minutes); rust/crates/server/src/broker_reads.rs:216 (read at every page open and every 5 minutes while open); rust/crates/book/src/statements.rs:215 (store_cash inserts a statements row and a statement_cash row per currency); rust/crates/book/src/statements.rs:327 (stated(): full scan of the account's cash statements, all parsed and sorted, to pick two)
- impact: On a Raspberry Pi the book grows by megabytes a month of identical balance rows, every engine rebuild spends time scanning and sorting them, and the file's 'every fact a figure was computed from' promise is diluted by rows no figure reads (only the newest is ever used).
- proposal: Write a cash or buying-power statement only when it differs from the newest one (as store_account_days already does), keep at most one per account per day beyond the newest, add an index on statements (account_id, kind, stated_at DESC) and on buying_power (account_id, stated_at DESC), and have stated() ask for 'ORDER BY stated_at DESC LIMIT 1' instead of loading the table.
- ux-conflict: False 
- owner decision: -
- confidence: high

### storage-A-4 [high/performance] Every book or cache access opens two fresh SQLite connections instead of borrowing from the pool that already exists
- status: contested — code: refuted (Accurate (figures.rs:206-215 Book::open_in / MarketCache::open per call; migrate.rs:112-124 two connections and identify twice; pool.rs:96-130 exists and app.rs:176 uses it for the cache only; events.rs:296, due.rs:102) ) | std: confirmed
- standard: Long-lived connections with a per-connection prepared-statement cache are the SQLite norm (sqlite.org: opening a connection re-reads and re-parses the schema; sqlx, r2d2, Diesel all pool); one open per request is what web frameworks are told not to do.

### storage-A-5 [medium/performance] synchronous=FULL is applied to the refetchable market cache, so every quote, close and outcome is an fsync the data does not need
- status: confirmed — code: corrected (The book half (one IMMEDIATE transaction per record, atomically pub(crate)) is storage-B-2's root cause and the per-quote/per-outcome commits are storage-B-7's; both are kept. What is A-5's own is the pragma choice: sqli) | std: corrected (The mechanics are verified: open_db sets synchronous=FULL for every connection including the cache (lib.rs:44); store_quote (cache.rs:226) and won (cache.rs:486) are autocommit, record() is its own transaction (cache.rs:)
- standard: SQLite's pragma documentation: 'The synchronous=NORMAL setting is a good choice for most applications running in WAL mode'; in WAL mode NORMAL is durable against application crash and consistent after power loss, losing at most the commits since the last checkpoint. A cache whose contents can be fetched again (the team's own definition of market.db, docs/architecture.md §6) has no durability requirement at all; the durability argument in lib.rs's comment ('a thesis or a grade cannot be fetched again') is the book's, not the cache's.
- observed: open_db_hooked (rust/crates/sqlite/src/lib.rs:26-45) is the one way every store is opened and sets `synchronous = FULL` unconditionally (line 44); MarketCache::open, the pool's prepare and Figures::cache all go through it. In WAL mode with FULL every commit fsyncs the WAL, so each store_quote (cache.rs:226, autocommit), won (cache.rs:498), store_read (cache.rs:582) and record() (cache.rs:523, its own transaction) is a flush; the per-pass count is storage-B-7's. The book's own per-record transactions are storage-B-2's.
- evidence: rust/crates/sqlite/src/lib.rs:44 (pragma synchronous = FULL for every connection, the market cache included); rust/crates/sqlite/src/lib.rs:11 (the comment justifies FULL by the journal's thesis or grade, which lives in the book, not ); rust/crates/sources/src/cache.rs:1 (module header: the cache holds what 'can be asked again'); rust/crates/sources/src/cache.rs:226 (store_quote: one autocommit write, hence one fsync, per quote); rust/crates/sources/src/cache.rs:523 (record(): a transaction, hence an fsync, per request outcome); rust/crates/book/src/lib.rs:126 (atomically is pub(crate) (the batching gap is storage-B-2))
- impact: On an SD card every quote pass and every source outcome pays a 5-20 ms flush and a card write for facts that would be refetched anyway; the fsync budget the book needs for the person's own entries is spent on the cache.
- proposal: Give open_db a durability parameter: FULL for the book, NORMAL for the market cache (WAL keeps it consistent; a power cut loses only the last few seconds of cache writes, which the next pass refills). Pair it with B-7's per-pass transaction so a quote pass is one commit.
