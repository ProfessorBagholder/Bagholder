# Design: the earlier app gone, every account read the same way, and the page saying where the book stands

Clone: `/tmp/claude-1005/-home-md-dev/12a8decb-6b2e-51e6-96e2-82398e1475b1/scratchpad/r571` at `2255a88` (origin/master). Paths below are relative to it.

## Verdict

Two releases. **2.10.0** deletes the earlier app's rows in one book migration (037) and every reader and writer of its file in the same release, reverts the two work-arounds (#575, #586) and the closed-account exception they stood on, reads every account the broker lists the same way, states a closed account as holding nothing so the book's figures in it are checked like any other's, and puts one dated line on the page: `Matches Wealthsimple as of <day>`, or why not. **3.0.0** removes migration 037 and the 36 before it by starting the book's schema from a base at version 37, so a book older than that is refused and told to open 2.10.0 first. About 45,800 lines go; about 1,760 come in, of which about 650 are hand-written (the rest is the schema snapshot each migration must commit, `rust/crates/book/src/schema.rs:1-3`).

Nothing re-runs at start, nothing waits on a condition, nothing keeps an earlier-app row, and no figure can be wrong without the header saying so.

## What happens to your book, step by step

Today your book holds 6,156 rows of source `bagholder-import`: 5,867 superseded (Wealthsimple's own row of the same activity is used instead), 288 removed (card rows Wealthsimple no longer lists), and 1 live: the leaving side of the holding moved on 2025-06-16 out of the managed RESP, since closed, into the self-directed RESP (`docs/plans/remove-the-earlier-app.md:14-19`). Only the live one still produces a figure: a superseded or removed record has no transactions, because the book deletes them when it supersedes or removes it (`rust/crates/book/src/records.rs:500-507`; transactions are read from live records only, `records.rs:579-583`).

**1. You install 2.10.0.** Before the migration runs, the whole book is copied to `snapshots/` beside it (`rust/crates/sqlite/src/migrate.rs:178-180`, `:249-267`); an update that does not come up puts the previous version and that copy back (`SPEC.md` versions-and-the-update-check-7, `docs/architecture.md:103`). Migration 037 then runs in one transaction (`migrate.rs:216-237`) and:
- deletes every `bagholder-import` record with everything hanging off it (the exact SQL is in "The data step");
- orphans a trade anchored on the one live record, if there is one, with its journal entry kept, exactly as Clear data does (`rust/crates/book/src/clear.rs:165-169`; test `clearing_the_broker_s_records_keeps_the_journal_orphaned_and_the_next_pull_reads_in_full`, `rust/crates/server/src/clear.rs:579-600`). A transfer out is not an opening (direction −1, `records.rs:80-91`; a trade anchors only on an opening, `rust/crates/book/src/trades.rs:57-61`), so the expected count is none; the counting query (query 2 in the book report) says before the PR merges;
- drops the two `legacy_key` columns and their indexes (`rust/crates/book/migrations/001-the-book.sql:195, 201, 206, 209`), the only columns that exist for the earlier app;
- empties `activity_reads`, so every account counts as never read in full and the next pull reads each whole (`rust/crates/broker/src/pull.rs:190-193`, `:215`), which is what Clear data already does to make "the next pull read everything again" (`rust/crates/book/src/clear.rs:204`; `SPEC.md` pages-24);
- removes the two settings rows that record earlier-app repairs (`repair.carried-notes-reattached`, `rust/crates/server/src/legacy_import.rs:359`; `carried.told-by-listing`, `rust/crates/server/src/carry.rs:325`).
Every reference is checked before the transaction commits (`migrate.rs:199-213`), and the migration is recorded with the app version (`migrate.rs:230-237`).

**What the page shows now.** The server builds the figures whole from the book (`rust/crates/server/src/figures.rs:259-262`). The holding moved on 2025-06-16 is in the self-directed RESP (its arrival is Wealthsimple's own row) and still in the managed RESP, because the leaving leg was the import's and is gone (`docs/plans/remove-the-earlier-app.md:21`). The header's sync line reads `Not yet checked against Wealthsimple`: no account has a complete read, so every cash check is pending (`rust/crates/engine/src/equity.rs:140-144`, `:159-172`; `cash_read` needs a read, `rust/crates/book/src/statements.rs:627-635`). A pull starts at once, because an account the book has never read in full makes a pull due now, as a first pull is due now (`rust/crates/server/src/broker_reads.rs:550`, "never pulled"). The header shows each step as it goes (`Step::Activity { account, n, of }`, `rust/crates/broker/src/lib.rs`, `broker_reads.rs:347`).

**2. The first pull.** Every account Wealthsimple lists, the closed managed RESP included, is read from the beginning. A row the book already holds as it is costs nothing more (`pull.rs:250-256`, `held` at `pull.rs:549-555`). The new rows are the ones Wealthsimple added since each account's last full read: the managed RESP's leaving row of 2025-06-16 (`ASSET_MOVEMENT`, `SOURCE`, `COMPLETED`), which Wealthsimple lists now, is among them. It is stored as Wealthsimple's own record; with both rows present the mapping books one leg in each account (`rust/crates/wealthsimple/src/mapping.rs` `transfer`, from line 857; held by `rust/crates/wealthsimple/tests/mapping.rs:659`), and the two legs are linked as one move (`pull.rs:863-879`). The managed RESP's units in the book return to nothing. The pull also stores, for each closed account, Wealthsimple's statement that it is closed as a statement of no cash and no units (new, below), so the book's figures in it are compared with that. At the owner's size (about 6,000 rows, pages of 100 at no less than 150 ms apart: `rust/crates/wealthsimple/src/client.rs:241`, `:18`, `:100-105`) the feeds take about nine seconds; rows unchanged cost no further reads.

The rows and the statements read with them reach the figures in one write (`broker_reads.rs:403`), and the header then reads `Synced just now · Matches Wealthsimple as of 2026-10-20` when every account's cash in every currency and every holding's units equal what Wealthsimple states. If anything differs, the line is red and names it, as today: `FUND in the managed RESP: Wealthsimple states 0 units, the book holds 10.` (`rust/crates/server/src/status.rs:201-237`; `SPEC.md` pages-13), standing until a read resolves it (pages-8).

**3. Every later pull** reads every account from its last full read; a closed account costs one request that answers nothing new. A row Wealthsimple adds to a closed account later is read because the account is read, never because another row gave a reason.

**4. You install 3.0.0** (after both copies are on 2.10.0). A book at version 37 opens with nothing to migrate. A book older than 37 is refused on the page, naming 2.10.0 as the version to open it with first (`docs/architecture.md`, §15: "a book it cannot open ... the page says so instead of loading").

**If the leaving row is still not listed** in the full read (the open question of `accountScope`, `rust/crates/wealthsimple/graphql/FetchActivityFeedItems.graphql:2`), nothing is inferred: the managed RESP keeps the units in the book, its statement of nothing makes that a difference, and the header says it in red until it is resolved. That is the design's point: the figure is wrong in the open, not silently.

## The data step: migration 037

`rust/crates/book/migrations/037-the-book-s-own-records.sql`, about 40 lines, modelled on Clear data (`rust/crates/book/src/clear.rs:152-233`), run with references off and checked before commit (`migrate.rs:191-194`, `:199-213`). Order matters: the two updates read `trades.anchor_record` and `adjustments.applies_record`, which point at the ids about to go; `adjustment_legs` before `adjustments` (`rust/crates/book/schema/v36.sql:116`); `link_records` before `links` (`v36.sql:311`); every table with `REFERENCES source_records(id)` before `source_records` (`v36.sql:122, 259, 312, 441, 451, 456, 463, 467, 528, 614, 640, 642`).

```sql
CREATE TEMP TABLE cleared AS SELECT id FROM source_records WHERE source = 'bagholder-import';
UPDATE trades SET anchor_record = NULL, anchor_leg = NULL, anchor_instrument = NULL,
       orphaned_reason = 'the record it opened on was cleared'
 WHERE anchor_record IN (SELECT id FROM temp.cleared);
INSERT INTO record_problems (record_id, code, detail)
SELECT a.record_id, 'adjustment-target-gone',
       'the transaction it explains, ' || a.applies_record || '/' || a.applies_leg || ', was cleared'
  FROM adjustments a WHERE a.applies_record IN (SELECT id FROM temp.cleared)
   AND a.record_id NOT IN (SELECT id FROM temp.cleared);
DELETE FROM transfer_links WHERE out_record IN (SELECT id FROM temp.cleared) OR in_record IN (SELECT id FROM temp.cleared);
DELETE FROM link_records WHERE record_id IN (SELECT id FROM temp.cleared);
CREATE TEMP TABLE empty_links AS SELECT id FROM links WHERE id NOT IN (SELECT link_id FROM link_records WHERE side = 'from');
DELETE FROM link_records WHERE link_id IN (SELECT id FROM temp.empty_links);
DELETE FROM links WHERE id IN (SELECT id FROM temp.empty_links);
DROP TABLE temp.empty_links;
DELETE FROM instrument_sightings WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM adjustment_legs WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM adjustments WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM record_problems WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM record_refs WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM record_revisions WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM transactions WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM record_holds WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM record_orders WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM statement_holds WHERE record_id IN (SELECT id FROM temp.cleared);
DELETE FROM source_records WHERE id IN (SELECT id FROM temp.cleared);
DROP TABLE temp.cleared;
DROP INDEX trades_legacy_key; ALTER TABLE trades DROP COLUMN legacy_key;
DROP INDEX trade_groups_legacy_key; ALTER TABLE trade_groups DROP COLUMN legacy_key;
DELETE FROM activity_reads;
DELETE FROM settings WHERE key IN ('repair.carried-notes-reattached', 'carried.told-by-listing');
```

Why only the import's `link_records` rows go, then links with no `from` side: Clear data deletes a whole link either side of a cleared record (`clear.rs:182-185`), but `supersede_copies` (`pull.rs:751-784`) can put a CSV record on the same `from` side as an import record, and deleting that link would strip the CSV record's supersession (`rust/crates/book/src/links.rs:119-136`, `:140-147`, read by the CSV linker at `rust/crates/server/src/csv_import.rs:499`). A link left with only `to` rows must not stay either (`links.rs:150-157`; `records.rs:488-493`).

`DROP COLUMN` needs SQLite 3.35 or later; the book links SQLite bundled (`rust/crates/sqlite/Cargo.toml:14`, `rust/Cargo.lock:1506-1507`, `libsqlite3-sys 0.30.1`), which is past it. A dropped column must not be indexed, so each index goes first.

**Your own data cannot be detached by it.** Nothing of yours names a record: the journal hangs on a trade (`v36.sql:290-298`), tags on the journal (`:299-304`), groups on trades (`:590-602`), orders and brackets on nothing (`:380-412`), notifications and told marks on nothing (`:350-360`, `:584-589`), watchlist and tiles on instruments (`:646-649`, `:580-583`). A trade reaches a record only through `trades.anchor_record`, and no trade is anchored on a superseded or removed record, because supersede moves or orphans every anchored trade before it changes the state (`links.rs:58-74`, `:94`) and removal orphans them first (`records.rs:478-487`); afterwards nothing can anchor on it (`trades.rs:57-61`; a superseded record has no transactions, `records.rs:502-505`). The only rows of yours that go are `record_orders` rows of import records, which Clear data deletes the same way (`clear.rs:194`); the orders stay. Held by the migration test below, field for field.

What the migration does not do: `settle_names` and `settle_successions` run at the book's next write (`rust/crates/book/src/lib.rs:143-158`; the triggers queue the work, `v36.sql:770-772`, `:951-953`), and the engine builds whole at the start after it, so nothing is read from a stale derivation. `clear_unnamed` is not run; an instrument named only by import rows stays as a harmless row, and the import's accounts are Wealthsimple's own (`rust/crates/book/src/import/mod.rs:134-151`).

## The read rule, and what is reverted

**The rule** (replaces `pull.rs:184-221` and the closed-account premise in `docs/plans/stage-3b-wealthsimple.md:63`, "nothing for a closed account with no new activity"): every account the broker lists, open or closed, is read the same way on each pull: its activity from its last complete read (whole when it has none), lowered to the first day of any row of it not yet final (`pull.rs:215-219` stays). The loop at `pull.rs:184-209` collapses to one line per stated account, with its last complete read. A closed account's cash and holdings are what the broker states by closing it, nothing, stored as a cash statement and a units statement with the accounts read (`Book::store_cash`, `store_units`, `rust/crates/book/src/statements.rs:513-525`), the units once as of the pull's day when first stated closed and again only if its newest units statement is not empty; so the broker check covers it (`equity.rs:179` gates on a units statement existing; `:140-144` and `:159-172` on the cash). This follows what the statements module already assumes of a closed account (`rust/crates/broker/src/statements.rs:921-926`: "An account with no row in any month read holds nothing where the broker states it closed") and costs no request. `keys_of` and `statement_keys` take every stated account (`pull.rs:364-367`, `:377-385`), so a closed account whose book cash is not nothing has its monthly statements read and the movements the feed left out booked, as the LIRA withdrawals are (`SPEC.md` movements-the-activity-feed-leaves-out-2). The history clause that skips a closed account once it has a day stored (`pull.rs:489-494`) goes, so history too is read from its last day for every account. The book's account status follows the broker's statement on every pull (today set only when adding, `pull.rs:121-128`; the five-minute balances read keys off it, `pull.rs:909-911`), one `UPDATE accounts SET status` where it differs.

The mapping's version moves 13 to 14 (`rust/crates/wealthsimple/src/mapping.rs:95-98`), "a move's leaving side is booked from its own row only", so every stored record is derived again at the next open (`rust/crates/server/src/figures.rs:886-893`).

## How you are assured the numbers are right, on the page

Today the header says a time, `Synced 2 min ago` (`web/src/App.svelte:314`), and otherwise only failures (`status.rs:182-191`); nothing positive and dated exists (grep of `web/src` and `rust/crates/server/src`). The practice in the category is a positive, dated reconciled state: YNAB marks reconciled transactions with a lock and says reconciling "provides assurance that the numbers in your plan are correct" (https://support.ynab.com/en_us/getting-started-with-reconciling-accounts-an-overview-Sy3JWx4Js); Quicken marks a reconciled transaction with an `R` (https://info.quicken.com/win/find-out-if-a-transaction-has-cleared); Beancount keeps a dated balance assertion in the ledger (https://beancount.github.io/docs/beancount_language_syntax/, Balance Assertions). Bank reconciliation is the term (https://openstax.org/books/principles-financial-accounting/pages/8-6-define-the-purpose-of-a-bank-reconciliation-and-prepare-a-bank-reconciliation-and-its-associated-journal-entries).

**The rule** (added to `SPEC.md` §4 beside pages-13): when no failure stands, the sync line also says where the book stands against the broker, in one of three states, computed from the broker check every build already runs (`equity.rs:130-214`; `figures.checks`):
- `Synced 2 min ago · Matches Wealthsimple as of Oct 20`: every account's cash in every currency and every holding's units equal what Wealthsimple states, nothing pending; the day is the earliest day any account's units are stated as of (`BrokerAccount.held_as_of`, `rust/crates/engine/src/input.rs:793-796`), the cash being checked at the last full read (`SPEC.md` pages-16).
- `Synced 2 min ago · Checking against Wealthsimple`: a statement is newer than an account's last full read, or a difference waits for confirmation (`BrokerCheck.pending`, `equity.rs:117-124`; `Difference::pending`).
- `Not yet checked against Wealthsimple`: no account has a statement at its last full read (`cash_read` none for every account).
A difference standing is said as today, in red, naming the account and both figures (pages-13), and takes the line (pages-21). Nothing appears and goes (pages-8; `docs/decisions.md:33`).

**Built as**: a `checked` field on `Status` (`rust/crates/server/src/status.rs:19-55`; the page's type is generated into `web/src/lib/generated/status.ts`), computed in `status()` from `f.read(...)` beside `broker_failures` (`status.rs:136`), about 40 lines; `syncLine()` in `web/src/App.svelte:308-315` adds the suffix, about 6 lines. No new read, no timer, no request: the check and the statements it reads already exist.

For a closed account the sentence reads `X in the managed RESP: Wealthsimple states 0 units, the book holds N.`, which is what Wealthsimple states by closing it; the engine's account input carries no status (grep of `rust/crates/engine/src/input.rs`), so the word "closed" is not added to the sentence in this design.

The check says the difference once confirmed; the person's remedy today is Clear data → Wealthsimple records (pages-24), which this design makes read at once. - **Stating a closed account as holding nothing** rests on what closing means and on `statements.rs:921-926`; `FetchAccountsWithBalance` was never asked for a closed id (`rust/crates/wealthsimple/graphql/FetchAccountsWithBalance.graphql:2-3`; no recorded reply). - **`carry_told_by_listing`** (`carry.rs:322-423`) is retired, not moved: it is a one-time repair recorded in settings (`:383`), done on your two machines at every start since it shipped; a fresh book has nothing to carry.
