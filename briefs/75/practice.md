## 1. Retiring one-time migration or import code

The documented pattern across the projects checked is the same three steps: (a) ship the migration and keep it until a stated floor version has been reached by every installation, (b) replace the accumulated history with a baseline snapshot (a schema file), (c) delete the migration code after the floor. No project checked documents keeping a one-off migration forever; GitLab comes closest, and even it deletes by squashing at each required stop. None of the sources addresses what to do with the data rows a one-time import produced; they all speak of schema/code, not records.

**GitLab (required upgrade stops).** https://docs.gitlab.com/update/upgrade_paths/ : "Some `major`.`minor` versions are required stops for some or all environments because there are fixes for issues relating to the upgrade process." and "Upgrade paths include required upgrade stops, which are versions of GitLab that you must upgrade to before upgrading to later versions." The procedure is three numbered steps: "Upgrade to the required upgrade stop after your current version." / "Allow the background migrations for the upgrade to finish." / "Upgrade to the next required upgrade stop." GitLab's development docs then tie deletion to those stops. https://docs.gitlab.com/development/database/migration_squashing/ : "Migration squashing combines multiple database migrations into a single schema definition"; the example given is "at the 18.8 required stop, migrations are squashed up to `origin/18-2-stable-ee`" (two required stops back); the Rake task "Updates `db/init_structure.sql` with the squashed schema" and "Removes all migrations from the previous version". Between squash points the rule is the opposite: https://docs.gitlab.com/development/database/deleting_migrations/ : "it's not possible to delete existing migrations, as that could lead to:" "Schema inconsistency" and "Leaving a record on the `schema_versions` table that points to a migration that no longer exists in the codebase." and "Instead of deleting, we can opt for disabling the migration."

**Django (squashmigrations).** https://docs.djangoproject.com/en/5.2/topics/migrations/ : "Squashing is the act of reducing an existing set of many migrations down to one (or sometimes a few) migrations which still represent the same changes." The deletion rule is explicit: "The recommended process is to squash, keeping the old files, commit and release, wait until all systems are upgraded with the new release (or if you're a third-party project, ensure your users upgrade releases in order without skipping any), and then remove the old files, commit and do a second release." The command's own output: "Once you are sure all instances of the codebase have applied the migrations you squashed, you can delete them."

**Rails (schema file as baseline).** https://guides.rubyonrails.org/active_record_migrations.html : "Migrations, mighty as they may be, are not the authoritative source for your database schema." "Your database remains the source of truth." Section "Old Migrations": "The `db/schema.rb` or `db/structure.sql` is a snapshot of the current state of your database and is the authoritative source for rebuilding that database." "This makes it possible to delete or prune old migration files."

**Nextcloud.** https://docs.nextcloud.com/server/latest/admin_manual/maintenance/upgrade.html , heading "Approaching Upgrades": "Nextcloud must be upgraded step by step:" "You cannot skip major releases."

**Home Assistant.** https://www.home-assistant.io/more-info/unsupported/home_assistant_core_version/ : "Migration code that converts YAML-based integrations to modern UI-based configuration is only available for 6 months after deprecation, which corresponds to 6 Home Assistant Core releases." "If you're significantly behind and have YAML-based integrations that need migration, update in increments of no more than 6 releases at a time (for example, from Home Assistant Core 2024.2 to 2024.8, then to 2025.2)." "At a minimum, update within 6 months (6 release cycles) to ensure you don't miss automatic YAML integration migrations." Also "Supervisor considers Home Assistant Core versions older than 24 months (approximately 24 releases) as unsupported." This is the clearest documented case of migration code with a stated lifetime after which it is removed.

**Firefox.** https://www.firefox.com/en-US/firefox/67.0/releasenotes/ : "Firefox will now protect you against running older versions of the browser which can lead to data corruption and stability issues." The support article https://support.mozilla.org/en-US/kb/dedicated-profiles-firefox-installation (compatibility.ini, --allow-downgrade) would not render for the fetch tool, so its wording is unconfirmed.

**Signal.** No support page found. The Signal-Desktop source does carry a dialog for the reverse case (data newer than app): https://github.com/signalapp/Signal-Desktop/commit/503620fe00fa05b658d2b1acb8f631899925a1a4 string `icu:databaseError__startOldVersion`: "The version of your database does not match this version of Signal. Make sure you are opening the newest version of Signal on your computer." No minimum-version or migration-retirement policy found.

**Bitwarden.** https://bitwarden.com/help/bitwarden-software-release-support/ : "At a given time, Bitwarden maintains the current major server version and the previous 2 major server versions." and "Self-hosted instances that do not update client and server versions in accordance with the Bitwarden version support policy risk introducing a client change that is incompatible with their server." No upgrade-path or skip rule found.

## 2. Why "everything since day X" is unsound, and the sound designs

The vendors' own docs state three facts that break a date-window read: records are removed after they were delivered, records are modified in place (including their date), and a pending record becomes a different posted record.

**Plaid.** https://plaid.com/docs/api/products/transactions/ : "All new implementations are encouraged to use /transactions/sync rather than /transactions/get." For the date-based endpoint: "a removed transaction will no longer appear in /transactions/get." (a since-X read cannot see a removal). The sync endpoint: "The /transactions/sync endpoint retrieves transactions associated with an Item and can fetch updates using a cursor to track which updates have already been seen." with `added`, `modified`, `removed` each defined as "Transactions that have been [added/modified/removed] ... since `cursor` ordered by ascending last modified time." https://plaid.com/docs/transactions/ : "In addition to added transactions, these subsequent updates may also include removed or modified transactions." and, of a refresh, "This creates new pending transactions, moves existing pending transactions to posted, and triggers webhooks." https://plaid.com/docs/transactions/transactions-data/ : on posting, sync returns "the pending transaction's `transaction_id` in the `removed` field of the response" and "the new posted transaction in the `added` section of the response"; "a posted transaction cannot necessarily be considered immutable." https://plaid.com/docs/transactions/sync-migration/ : "While /transactions/get provides all transactions within a date range" sync "instead uses a cursor to provide all new, modified, and removed transactions that occurred since your previous request." and "Updates returned by /transactions/sync can be patched into your database, allowing you to avoid a complex transaction reconciliation process".

**Stripe Financial Connections.** https://docs.stripe.com/api/financial_connections/transactions/object : status `void`: "This transaction has disappeared and no longer affects the account's balance."; `transaction_refresh`: "The token of the transaction refresh that last updated or created this transaction." https://docs.stripe.com/financial-connections/transactions : "As long as you remain subscribed to transaction data, Stripe initiates a new refresh every day." and the incremental read is by refresh token, not date: "To retrieve only new or updated transaction data since your last refresh, pass the `transaction_refresh` identifier provided by your last observed financial_connections.account.refreshed_transactions webhook event object to the list API".

**Teller.** https://teller.io/docs/api/account/transactions : "When a pending transaction posts, its date often changes to the posting date." "Teller maintains stable transaction IDs." and the sync advice: "Expand the window 7-10 days beyond your last sync", matching on id, inserting new and updating existing records.

**Akahu.** https://developers.akahu.nz/docs/accessing-transactional-data : "Unfortunately, banks often mutate a transaction in the days (or weeks) following its posting." "The `date`, `description`, and `balance` of a transaction may change during this period." "Your code should expect to handle addition, modification, and deletion of transactions when fetching them from Akahu." and for pending items "it is recommended that you completely rebuild your local copy of this data".

Sound designs, as documented: a change feed with a cursor (Plaid sync, Stripe transaction_refresh[after]); or stable ids plus an overlapping re-read window with upsert and delete (Teller, Akahu); plus periodic full rebuild of the volatile part (Akahu). A per-account "last read date" is what all four vendors steer away from.

## 3. How consumer finance apps assure the person the numbers are right

The common practice is a positive, dated state, not just errors: a per-transaction "reconciled" flag plus a point in time at which the app's balance was shown equal to the institution's, and an explicit adjustment entry when it is not.

**YNAB.** https://support.ynab.com/en_us/reconciling-accounts-a-guide-BJFE3fHys : reconciling is "the process of comparing the transactions and balances at the bank with the transactions and balances in YNAB." Pressing Reconcile "puts green lock icons next to reconciled transactions" and "tells YNAB not to import previous transactions, even if the bank tries to send them again." Mismatch: "Clicking that will automatically create a Reconciliation Balance Adjustment to correct your balance." Afterwards "YNAB will only import transactions dated up to three days prior to your last reconciled transaction." https://support.ynab.com/en_us/getting-started-with-reconciling-accounts-an-overview-Sy3JWx4Js : "Once transactions have been reconciled in YNAB, they are locked and marked with a lock icon." and "it provides assurance that the numbers in your plan are correct."; recommended "at least once a week."

**Beancount.** https://beancount.github.io/docs/beancount_language_syntax/ , section Balance Assertions: "It tells Beancount to verify that the number of units of a particular commodity in some account should equal some expected value at some point in time." "When processing the list of entries, if Beancount encounters a different balance than this for USD it will report an error." "a balance assertion, like all other non-transaction directives, applies at the beginning of its date". On double-booking from imports: "regularly inserting a balance assertion will catch that problem every time". Beancount is the errors-only model, but the assertion line itself is a positive, dated statement kept in the ledger.

**Quicken.** https://www.quicken.com/support/reconciling-account-quicken-windows : "When you balance, or reconcile, an account, you compare your Quicken account records against your current bank statement"; "Click Done if the difference in the lower-right corner is zero." https://info.quicken.com/win/find-out-if-a-transaction-has-cleared : "An R in this column means that Quicken has reconciled the transaction" and "The Opening Balance transaction that Quicken creates when you set up an account is also marked with an R."

**Monarch.** https://www.monarch.com/blog/transaction-review : "The new transaction review system lets you mark transactions as needing review or already reviewed." The word "reconcile" does not appear. **Lunch Money.** https://support.lunchmoney.app/setup/accounts/faq.md : "reconcile" does not appear; balances of manual accounts are "updated automatically when you add, remove or update a transaction". **Copilot Money.** Not found.

**Accounting term.** The standard term is bank reconciliation (statement). https://openstax.org/books/principles-financial-accounting/pages/8-6-define-the-purpose-of-a-bank-reconciliation-and-prepare-a-bank-reconciliation-and-its-associated-journal-entries : "The bank reconciliation is the internal financial report that explains and documents any differences..." and "after the bank reconciliation is prepared accurately, both the bank balance and the company balance will be the same amount." https://en.wikipedia.org/wiki/Bank_reconciliation : "A bank reconciliation statement is a statement prepared by the entity as part of the reconciliation process which sets out the entries which have caused the difference between the two balances."

## 4. Source of record and derived data

**Fowler.** https://martinfowler.com/eaaDev/EventSourcing.html : "Event Sourcing ensures that all changes to application state are stored as a sequence of events." Under Complete Rebuild: "We can discard the application state completely and rebuild it by re-running the events from the event log on an empty application." and "Since an application state is purely derivable from the event log, you can cache it anywhere you like."

**Kleppmann.** The Part III introduction ("Systems of Record and Derived Data") is at https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/part03.html ; that page returned HTTP 403 to the fetch tool, so its exact wording is unconfirmed here (a search-engine index of that URL matched the phrases "system of record", "also known as source of truth", "holds the authoritative version of your data"; a reader highlight on Goodreads carries "If you lose derived data, you can recreate it from the original source"). Confirmed from Kleppmann's own site, same principle: https://martin.kleppmann.com/2015/03/04/turning-the-database-inside-out.html : "A materialized view is just a cached subset of the log, and you could rebuild it from the log at any time." and the views are "data structures that are derived from the data in the log, and optimized for fast reading."

## 5. Wealthsimple activity feed

Nothing official. developers.wealthsimple.com does not resolve (DNS ENOTFOUND on fetch). The help article https://help.wealthsimple.com/hc/en-ca/articles/39449252453019-View-your-account-activity (read via the Zendesk JSON endpoint) says "You can view all deposits, withdrawals, trade orders, corporate actions, and any other activity", "You can now see a dedicated pending section at the top of your Activity feed.", and "Transfers between Wealthsimple accounts before January 1, 2025, are on separate activity lines." It says nothing about closed accounts, backfilled rows, or how far back the feed goes.

Open-source clients. https://raw.githubusercontent.com/gboudreau/ws-api-python/main/ws_api/graphql_queries.py declares `query FetchActivityFeedItems($first: Int, $cursor: Cursor, $condition: ActivityCondition, $orderBy: [ActivitiesOrderBy!] = OCCURRED_AT_DESC, $accountScope: AccountScope = OWN)` and requests, among others, `accountId, amount, amountSign, canonicalId, occurredAt, opposingAccountId, status, subType, type, unifiedStatus, externalCanonicalId, transferType, transferReason, rejectionReason, estimatedCompletionDate`. https://raw.githubusercontent.com/gboudreau/ws-api-python/main/ws_api/wealthsimple_api.py builds the condition as `"condition": {"startDate": self._iso_z(start_date), "endDate": self._iso_z(end_date), "accountIds": account_id}`, paginates with `variables["cursor"] = end_cursor` from `pageInfo.endCursor`, and filters client-side with `excluded_statuses = {"rejected", "cancelled", "expired"}` and `act_type != "LEGACY_TRANSFER"`. No comment in either file mentions closed accounts, backfilled rows, or what startDate is compared against (occurredAt vs creation time): not found. https://github.com/gboudreau/ws-api-php README shows only `$acts = $ws->getActivities($account->id);` with the comment "Activities are sorted by OCCURRED_AT_DESC by default; let's reverse". The library is headed "Unofficial Wealthsimple API Library for Python" / "...for PHP".

- Kleppmann's exact Part III wording (system of record / derived data recreated from source) could not be read from O'Reilly (HTTP 403); someone with the book or an O'Reilly login should confirm the quote before it is cited verbatim.
- Firefox's support article on compatibility.ini and --allow-downgrade would not render for the fetch tool; its exact wording is unconfirmed.
- None of the migration-retirement sources addresses the data rows a one-time import produced (as opposed to schema and code); whether to delete superseded import records is a product decision, not a documented convention found here.
- Wealthsimple's FetchActivityFeedItems startDate semantics (compared against occurredAt or against record creation time) and whether rows are backfilled into past dates are undocumented anywhere public; only an experiment against the live feed can settle it.
- Whether the Wealthsimple feed returns activity for closed accounts when their ids are passed in condition.accountIds is undocumented; the owner's observation that the leaving row now appears suggests yes, but no public source states it.
- Copilot Money's help pages on any reconciled state were not found; Lunch Money and Monarch document review states but no reconciliation.
