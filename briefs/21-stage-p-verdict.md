## Required changes

1. **Budgets from the app's own cadences; RAIL only where a person waits.** RAIL's numbers are for a browser page answering a person. Three of the six operations never answer a person: `brokers`, `price_changed` and `Feed::step` run inside loops with cadences the app itself states (`SPEC.md`: cash and buying power every five minutes while a page is open; quotes every minute; `due.rs`). The budget for each is derived from that cadence and the book's size, both facts: one pass over every priced holding must finish inside its own cadence at four times the owner's size on a Pi, so `price_changed` ≤ cadence ÷ (holdings at that size), `brokers` ≤ the balances cadence ÷ accounts, `Feed::step` ≤ the time between signals at the measured signal rate. "RAIL idle chunk" is not a source for a server loop. RAIL stays for startup (5 s, first load), the added trade and the import (1 s to the stream, 100 ms for the request's own answer): a person is waiting there. Each budget's line in `capacity.rs` names which fact it comes from.
2. **The Pi factor covers CPU only; the growth rule is the gate.** `PI_SLOWDOWN` = 2.1 is a single-core ratio between two machines with NVMe and SD storage. On the Pi this app's cost is reading a 1.8 GB book from an SD card at single-digit MB/s on random reads; a wall budget scaled by 2.1 passes in CI and fails on the Pi. So: the growth rule (VM steps and allocations, machine-independent) is the gate that fails a PR; wall time scaled by the factor is reported and holds only the operations where the person waits; and the table marks each operation as CPU-bound or IO-bound, with IO-bound ones also counting SQLite page reads (`SQLITE_DBSTATUS_CACHE_MISS` through rusqlite's status API, or `PRAGMA` stats) so an IO regression is a counted number, not a timed one. The factor stays a named parameter with its sources, marked "CPU only; not measured on hardware".
3. **Cache the built books in CI.** Building the owner preset and four times it through the real pull on every PR, before seven timed runs of each operation, will cost the arm job tens of minutes. Cache each built book under `actions/cache` keyed by the generator's source hash, the seed and the sizes, so a PR that does not touch the generator pays only the measurement. The plan already makes the build deterministic, which is what makes the cache sound.
4. **Spec ids must not render as text.** `{#figures.avg-cost}` at the end of each line is Pandoc attribute syntax; GitHub's Markdown renders it as literal text, so the rendered spec would carry a bracketed tag on every rule line. Use an invisible anchor (`<a id="figures.avg-cost"></a>`) or an HTML comment, whichever the `spec_ids` test reads; the anchor also makes each rule linkable, which is what the ids are for.
5. **One issue per root cause, not per finding.** Brief 15 has 299 findings, 35 already merged as one root cause with another, and many more that share a cause (the balances table, the symbol-keyed cache, the write-token constant). Filing one issue per finding fills the tracker with duplicates nobody can work from. File one issue per root cause, carrying every finding id it covers, the severity of the worst, the product or standard named, the test that will hold the fix and the `stage-N` label; the PR lists the finding-to-issue map and the findings a merged stage fixed, with the commit.
6. **`cargo audit` fails the job on vulnerabilities, reports warnings.** Its default exit code already does this; the plan's "a finding fails the job" would fail on an unmaintained-crate warning the project cannot act on. Say which.
7. **The transfer rule from brief 20 is a follow-up, not lost.** Brief 20's item 3 was corrected on 2026-10-08, after decisions 6, 7 and 9 were built (2.4.0, 2.5.0): a transfer between accounts of the same registration continues the round trip, one across a registered boundary is a disposition at the broker's stated value (sources in `briefs/20/transfers.md`). It is engine behaviour, so it is gated: a short plan of its own, or an issue filed in Part F against stage 4 with the sources, whichever CTO prefers; not silently dropped.
